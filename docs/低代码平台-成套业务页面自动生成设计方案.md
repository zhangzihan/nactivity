## 1 背景与目标

本项目是一个面向复杂企业业务的模型驱动低代码平台，包含工作流引擎（`nactivity`）、后端服务（`src`）、前端编辑器（`coding`）三大部分。当前搭建一个业务页面（例如采购订单），实施人员通常需要手工完成以下步骤：

1. 先建立业务实体、定义字段与关系、点击部署完成物理建表；
2. 编写列表查询脚本与主记录查找脚本，再执行"分析"以得到字段元数据；
3. 打开空白画布，手工拖入控件、逐一配置字段绑定、显隐只读规则、按钮与动作；
4. 再单独配置权限、流程、打印模板等。

上述链路虽然灵活，但**操作成本高、专业门槛高、容易遗漏配置且一致性差**。尤其在客户希望"以最快速度得到一整套可跑通的业务功能"时，空白画布方式明显拖慢交付节奏。

### 1.1 本次设计目标

| 目标 | 说明 | 验收指标 |
|------|------|----------|
| 降低起步成本 | 从实体或查询一键生成"列表+编辑+详情+筛选"的成套页面包，而不是从空白画布开始 | 采购订单从实体到可运行页面 < 3 分钟 |
| 保持专业模式 | 自动生成只是起点，不取代原有设计器，保留手工接管与专业模式 | 生成后可切换专业编辑且不丢失配置 |
| 保证一致性 | 字段标题、格式、选择器、校验在页面、查询、权限中保持同一来源 | 改一次字段标题，三个页面同时生效 |
| 可持续演进 | 新增字段后可选择同步已有页面，不覆盖人工改动 | 新增字段后差异可视化，可逐项采纳 |
| 支持行业模块 | 与行业模块打包、安装、升级机制无缝衔接 | 安装采购模块时默认生成全套页面 |

### 1.2 非目标（不在本期范围）

- 不取代现有表单生成器与 XML 存储格式；
- 不实现完全可视化的拖拽重排（已有设计器承担）；
- 不承诺生成 100% 完美的复杂跨表编辑页，复杂场景仍需专业模式；
- 不在本次引入新的前端框架或换肤。

## 2 设计原则

设计遵循"**深度模块（Deep Module）**"思想：调用方只需一个很小的触发入口（实体右键/查询右键"生成成套页面"），背后封装复杂的推断、绑定、策略选择逻辑。

| 原则 | 说明 | 在本设计中的体现 |
|------|------|------------------|
| 最小接口 | 暴露给用户的入口越少越好，复杂度藏在模块内部 | 只暴露一个"生成成套页面"入口，策略参数折叠为预设场景 |
| 单一事实源 | 同一字段的标题、格式、选择器只定义一次 | 页面绑定优先读取实体字段语义（Semantic），不再副本拷贝 |
| 只生成不覆盖 | 生成系统只能生成新资产或建议变更，不能无提示覆盖人工接管内容 | 所有二次同步都走差异-采纳模式 |
| 向前兼容 | 不破坏现有实体、查询、表单 XML 结构 | 新增元数据放在扩展节点，老版本忽略即可 |
| 深度优于广度 | 先把"实体/查询→页面"这条链路做深做稳，再扩展到报表、打印等外围 | 首版只覆盖列表、编辑、详情、筛选四个核心页面 |

## 3 核心概念与领域模型

### 3.1 术语表

| 术语 | 英文 | 定义 |
|------|------|------|
| 业务实体 | Business Entity | 对应数据库表的领域对象，包含字段、关系、语义配置 |
| 查询/脚本 | Query / Script | 平台内的 SQL 或 SmartSql 查询定义，可返回列表或单条记录 |
| 页面包 | Page Bundle | 一次性生成的一组相关页面（列表+编辑+详情+筛选）+ 动作绑定 |
| 页面草稿 | Page Draft | 生成后处于草稿状态、尚未部署/发布的页面定义 |
| 字段语义 | Field Semantic | 字段在实体上的业务语义（单据编号、金额、币别、人员等） |
| 生成策略 | Generation Strategy | 针对不同场景选择字段分组、控件类型、默认列的策略集 |
| 接管标记 | TakenOver | 生成的元素被用户手工修改后，标记为不再被重新生成覆盖 |
| 引用选择器 | Lookup Selector | 针对引用类型（供应商、职员等）的共享选择器资产 |
| 生成清单 | Generation Manifest | 一次生成产生的资产目录与前后映射关系 |

### 3.2 核心对象关系

一个业务实体（或查询）通过生成器（`PageBundleGenerator`）产出一个**页面包**，页面包内部由多**页定义**组成；每一页定义与实体/查询形成绑定，并通过**生成清单**记录来源与变更轨迹。

| 领域对象 | 关键属性 | 持久化（File Provider / Redis Provider 双模式，均通过 IPageBundleRepository 抽象，不直接依赖底层存储） |
|----------|----------|--------------------------------------------------------------------------------------------------------------------------------|
| PageBundle（页面包） | BundleId, Name, SourceKind(Entity\|Query), SourceKey, Status, Version | File：L1 `PageBundles.xml` + L2 `pageBundles/{BundleId}/bundle.xml`（见 9.1 节）<br>Redis：`{appId}:pagebundle:{bundleId}`（Hash 头部）+ `{appId}:pagebundle:index`（Set 集合）+ `{appId}:pagebundle_detail:{bundleId}`（String 完整详情，可选）（见 9.5 节） |
| PageDefinition（页定义） | PageId, BundleId, PageKind, Layout, DataSource | 两种 Provider 下都**复用已有 FormDefine 存储，不新建资产**：<br>File：`forms/{FormId}/` + Forms.xml 的 Fields JSON 扩展属性<br>Redis：key `{appId}:form_define:{id}`（JSON 字符串）+ `{appId}:form_view:{formId}`，见 [RedisConnection.FormDefineKey](file:///d:/Project/MDD/9.0/src/Sys.Metadata.Redis/RedisConnection.cs#L83-L93)；TakenOver 扩展写在 Fields JSON 里 |
| FieldBinding（字段绑定） | FieldKey, ControlKind, ReadOnly, Required, LookupId, Semantic | 同 PageDefinition：沿用现有控件定义，在 Fields JSON 中扩展 `semantic` 与 `generatedFrom/takenOver` 属性（双 Provider 同一 JSON 结构，无差异） |
| GenerationStrategy（生成策略） | StrategyId, Scene, Preset, OverrideRules | 四层覆盖（双 Provider 一致）：<br>平台默认 → 项目级 JSON `config/page-generator-strategies.json` → 实体级扩展节点（entities/{Entity}.xml `<PageGenStrategy>` 或 Redis 对应 `{appId}:entity_schema:{name}` String 内容节点）→ Bundle 级 `strategy-override.json` / Redis `{appId}:pagebundle_strategy:{bundleId}` Hash 或 String |
| GenerationManifest（生成清单） | ManifestId, BundleId, CreatedAt, SourceSnapshot, AssetList | File：L2 `pageBundles/{BundleId}/manifest-{NNN}.json`（001 递增，天然可回滚，见 9.1 节 L2）<br>Redis：String（JSON）key `{appId}:pagebundle_manifest:{bundleId}:{NNN}`；`current_manifest_version` 存在 PageBundle L1 Hash 内 |

## 4 两种生成模式：从实体生成 vs 从查询生成

### 4.1 模式 A：从业务实体直接生成

**适用场景：** 用户已经通过"实体→部署"完成物理建表，需要快速得到一套标准的 CRUD 页面。生成器会基于实体字段 + 关系自动推断查询、动作、选择器与页面布局。

#### 4.1.1 入口与操作

1. 用户在"实体列表"或"实体设计器"的实体上右键：**生成成套页面**；
2. 弹出向导：选择场景（基础档案 / 主子表单据 / 流程申请 / 查询分析）→ 选择默认页面包 → 勾选是否同时生成**列表脚本 + 主键查找脚本 + 默认动作权限模板**；
3. 确认后展示"将要生成资产清单"，用户可删除不需要的项；
4. 一键确认，生成草稿包并打开统一预览。

#### 4.1.2 自动创建的资产

| 资产类型 | 命名约定 | 说明 |
|----------|----------|------|
| 列表查询脚本 | `{实体代码}_List` | 默认取非大文本字段，含分页与常见可筛选列；若为引用列，默认显示"名称"并保留外键 |
| 主键查找脚本 | `{实体代码}_GetById` | 按 ID 查单条，返回全部可写字段 + 引用显示列 |
| 列表页 | `{实体名称}列表` | 顶部筛选区（引用列→选择器，日期→范围，枚举→下拉）+ 数据表格 + 动作栏（新增/编辑/删除/导入/导出/刷新） |
| 编辑页 | `{实体名称}编辑` | 分组 Tab（基础信息/明细/附加信息）+ 保存/保存并新增/取消 + 必填校验 |
| 详情页 | `{实体名称}详情` | 只读卡片布局 + 打印入口 + 流程进度面板占位 |
| 动作权限模板 | `{实体代码}_动作模板` | 模板化角色操作权限（创建者可改、审批人可看等），需用户确认后应用 |
| 生成清单 | `{时间戳}_{BundleId}` | 记录以上资产及其来源快照，用于后续增量同步 |

### 4.2 模式 B：从查询/脚本直接生成

**适用场景：** 用户已经有成熟 SQL（如采购合同执行明细），希望快速得到 BI 风格的自助查询页/报表页。由于查询中可能包含计算字段、聚合列、跨表连接，本模式默认以**只读展示 + 多维筛选**为主，不直接生成可编辑页。

#### 4.2.1 入口与操作

1. 用户在"业务脚本"列表的脚本上右键：**生成成套页面**；
2. 先执行一次分析得到字段元数据，识别：实体字段 / 关联显示字段 / 计算字段（VIRTUAL_TABLE） / 聚合字段；
3. 弹出向导：选择页面类型（自助查询 / 主从报表 / 搜索详情跳转）→ 选择主实体（用于跳回编辑的链接锚点，可选）→ 勾选保存视图、收藏、导出；
4. 展示字段清单，允许用户拖拽调整默认列与分组。

#### 4.2.2 自动创建的资产

| 资产类型 | 命名约定 | 说明 |
|----------|----------|------|
| 查询页 | `{脚本名称}查询` | 顶部筛选器（Faceted Search 风格）+ 数据表格 + 个人/团队视图保存 |
| 详情面板（可选） | `{脚本名称}详情` | 单击行后弹出侧栏详情，只显示非表格主列的补充信息 |
| 跳转链接（可选） | `{主实体}编辑` | 如果用户指定主实体主键列，自动在该列生成跳转编辑页的链接并校验权限 |
| 导出配置 | 默认导出模板 | 按分析字段生成 Excel 导出字段映射，可后续覆盖 |

### 4.3 模式对比与选择策略

| 维度 | 模式 A：从实体生成 | 模式 B：从查询生成 | 推荐选择 |
|------|--------------------|--------------------|----------|
| 主要目标 | 标准 CRUD 业务单据/档案 | BI 风格查询/报表/分析 | 业务录入用 A，查询分析用 B |
| 可编辑 | 默认完整编辑能力 | 默认只读，跳转链接可选 | 写操作用 A，只读用 B |
| 对 SQL 依赖 | 自动生成默认脚本（可覆盖） | 完全基于已有 SQL | 有复杂 SQL 的场景优先 B |
| 权限建议 | 绑定"创建者/审批人/分配者"动作 | 只绑定查询范围和导出权限 | 权限模型在第 8 章融合 |
| AI 辅助建议 | 适合让 AI 建议字段分组与校验 | 适合让 AI 建议字段解释与筛选维度 | 第 12 章详述 |

## 5 生成的页面包（Page Bundle）组成

首版统一把页面包拆为"**核心四页 + 附加能力**"，避免一次性过宽范围导致不可维护。核心四页覆盖 80% 常见企业场景。

| 页面 | 页类型 | 主要区域 | 默认动作 |
|------|--------|----------|----------|
| 列表页 | List | 筛选区、快捷操作栏、数据表格、分页 | 新增、编辑、查看、删除、批量删除、导入、导出、刷新、保存视图 |
| 编辑页 | Edit | 面包屑、表单主体（分组/Tab）、明细表格、操作面板 | 保存、保存并新增、保存并提交、取消（带未保存确认） |
| 详情页 | Detail | 基础信息卡片、关联面板（明细、日志、附件、审批轨迹） | 编辑、打印、通过流程动作进入任务处理 |
| 筛选器资产（共享） | Filter Asset | 维度卡片 + 时间范围 + 搜索框 + 已选条件胶囊 | 重置、应用、保存为公共/个人视图 |
| 打印模板（附加） | PrintTemplate | 由平台现有打印模板生成器生成 | 打印、导出为 PDF |
| 流程挂点（附加） | BpmnHook | 状态变化触发 BPMN 启动/任务跳转动按钮 | 启动流程、处理任务、查看轨迹 |

### 5.1 列表页的智能默认

- 只取前 N 个字段（默认 10 个）作为列表默认显示列，按字段语义排序：**编号 > 名称/标题 > 关键引用（供应商/客户） > 日期 > 金额/数量 > 状态**；
- 长文本、附件、图片、富文本默认不进列表列，而是进详情/侧栏；
- 引用类型列默认显示**名称（NameColumn）**而不是 ID，ID 隐藏用于跳转；
- 每个列表都自带"列选择器"，允许用户在运行时显示更多列；管理员可改默认配置。

### 5.2 编辑页的智能分组

- 字段数 ≤ 12：单列滚动布局，无 Tab；
- 13–24：两组 Tab（基础信息 / 其他信息），按语义分组；
- > 24 或存在多个子表：主 Tab（基础信息） + 子表 Tab（按子实体名称命名） + 附加 Tab（附件/备注）；
- 所有 Tab 顺序可在"生成预览"中拖拽调整；一旦用户手工调整，该分组标记为 **TakenOver**，后续重新生成不再覆盖。

### 5.3 筛选器：APEX Faceted Search 思想

借鉴 Oracle APEX 的 **Faceted Search / Smart Filters**：筛选器不再是零散查询条件，而是"**维度卡片 + 已选胶囊 + 命中计数**"。每一个筛选维度有默认类型（下拉、范围、树、搜索框），按字段语义推断。

| 字段语义 | 默认筛选器类型 | 交互说明 |
|----------|----------------|----------|
| 状态/枚举 | 多选下拉 + 计数 | 展开显示每个状态的条数；支持多选 |
| 日期（下单日、创建日） | 范围选择器 + 快捷区间 | 快捷：今日/本周/本月/本季/本年/自定义 |
| 引用（供应商、部门） | 搜索下拉（LookUp） | 复用共享选择器；支持多选 |
| 数值（金额、数量） | 最小值–最大值范围框 | 两侧输入框；支持空值 |
| 文本（单号、名称、备注） | 顶部统一搜索框 | 模糊搜索，可限定字段范围 |
| 人员（创建人、业务员） | 员工选择器 | 支持按部门树筛选 + 搜索 |

## 6 生成流程与智能选择算法

### 6.1 总体流程（7 步）

| 步骤 | 名称 | 输入 | 输出 | 主要逻辑 |
|------|------|------|------|----------|
| S1 | 选择触发源 | Entity or Query | SourceKind + SourceKey | 区分实体/查询模式 |
| S2 | 推断场景 | 用户选择场景 Preset + 元数据 | 策略集 Strategy | 场景×元数据→策略；可覆盖 |
| S3 | 字段分类 | 字段列表 + 语义 + 关系 | 字段分组与默认页面归属 | 哪些进列表/编辑/详情/筛选 |
| S4 | 控件映射 | 字段分类结果 | 控件类型 + 默认配置 | 数据类型×语义→控件选择器 |
| S5 | 默认动作 + 权限模板 | 场景 + 关系 + 状态 | 默认动作列表 + 角色模板 | 单据=审核动作，档案=停用启用动作 |
| S6 | 生成资产 + 清单 | 以上结果 | PageBundle + Manifest | 生成器写入 XML 扩展节点 |
| S7 | 预览 + 用户采纳 | 清单 + 差异（二次生成时） | 用户确认后的草稿包 | 用户可取消/勾选具体项后再保存 |

### 6.2 字段分类算法

对于实体模式，字段首先按以下优先级归类，优先级从高到低：

1. **规则 1：主键（ID）** — 不在编辑页显示，列表页默认隐藏，详情页显示；
2. **规则 2：系统字段（CREATEDATE/CREATOR/UPDATEDATE/UPDATOR）** — 全部进详情页的"系统信息"折叠组，列表/编辑页不显示；
3. **规则 3：语义为"单据编号、名称、标题、状态、关键引用"的字段** — 默认进列表首屏列 + 编辑页基础信息组 + 筛选区；
4. **规则 4：语义为"币别、金额、数量"的字段** — 默认进列表且右对齐、带千分位，编辑页独立分组"财务信息"；
5. **规则 5：日期类字段** — 列表、编辑、筛选默认全部进入；
6. **规则 6：布尔、枚举、下拉** — 默认进筛选器；
7. **规则 7：长文本、富文本、图片、附件数组** — 默认进详情/侧栏；
8. **规则 8：子表（主从关系）** — 编辑页单独 Tab，详情页折叠面板；
9. **规则 9：查询模式下的 VIRTUAL_TABLE / 聚合字段** — 默认进列表与详情，不可编辑，筛选器按类型推断。

### 6.3 控件选择映射（按数据类型 × 语义）

| 数据类型 | 常见语义 | 默认控件 | 附加默认配置 |
|----------|----------|----------|--------------|
| String(≤50) | 单据编号/名称 | Input + 标签 | 必填、长度校验；编号型添加复制按钮 |
| String(≤50) + 引用 | 供应商/客户/职员 | LookUp 选择器 | 复用共享选择器；自动回填名称/编码 |
| String(>200) | 说明/备注 | TextArea | 可折叠；默认允许为空 |
| Int/Decimal | 金额/税率 | InputNumber | 金额千分位+币种符号，税率%，精度按语义 |
| Int/Decimal | 数量 | InputNumber | 数量支持小数位配置；关联单位 |
| Date/DateTime | 下单日/交货日 | DatePicker/Range | 默认允许空；交货日≥下单日校验 |
| Bool | 启用/停用 | Switch | 编辑页可操作；列表进 Badge |
| Enum | 状态/类型 | Select | 列表进 Tag/Badge；筛选器进多选下拉 |
| UUID(引用) | 外键 | LookUp | 复用共享选择器；保持名称/编码的显示列 |
| File/Image | 附件/图片 | Uploader | 多文件；大小与类型限制可配置 |

### 6.4 策略覆盖机制（项目级与实体级）

平台级提供默认策略（Preset：档案、单据、申请、分析），每个项目可在 `{项目}/config/page-generator-strategies.json` 中覆盖，也可在单个实体上用"生成策略"属性绑定。覆盖层级为：

> **平台内建默认 < 项目级策略 < 实体级单独覆盖 < 用户在生成向导中的临时勾选。**

## 7 生成后增量修改机制（可持续演进）

这是本设计与"一次性生成模板"最大的差异点：必须解决"生成后用户手工改了，后续实体新增字段如何安全同步"的问题。

### 7.1 核心机制：TakenOver 接管标记

生成器写出的每个控件、每个分组、每段动作绑定都会写入扩展节点：

```xml
<GeneratedFrom bundleId="xxx" manifestId="xxx" takenOver="false" />
```

一旦用户在设计器中手工修改该元素（包括改位置、改属性、改绑定），`takenOver` 置为 `true`。后续重新生成或同步时：

| 元素状态 | takenOver=false | takenOver=true |
|----------|-----------------|----------------|
| 字段标题/格式改动 | 自动跟随实体语义更新 | 保留用户覆盖值，提示用户是否统一 |
| 新增字段 | 按策略插入合理位置 | 新增字段会出现在差异清单中，用户单独勾选是否采纳 |
| 删除字段 | 移除绑定并标记废弃控件 | 保留控件，但以"红色警示"提示字段已失效，用户确认后删除 |
| 移动位置 | 按策略重新排布 | 保持用户位置，不移动 |
| 控件类型变更 | 按策略更新 | 不更新 |

### 7.2 差异-采纳交互（受 Git 影响）

1. 用户在实体/查询上点击**"同步页面包"**；
2. 系统展示三类差异：**新增（绿色 +）、变更（黄色 Δ）、删除（红色 −）**；
3. 每个差异点击可预览"新布局 vs 当前布局"；
4. 支持"**全部采纳新增、全部跳过手工接管项、仅采纳标题/格式统一**"三种快捷模式；
5. 采纳后写入新 ManifestId，保留历史回滚能力（回滚到上一版 Manifest 对应的 XML 快照）。

## 8 与现有平台能力的集成

### 8.1 与表单生成器的集成

**不重写表单生成器**。新增"生成成套页面"命令，在现有 `createformcommand` / `createformdialog` 的基础上做批量封装，复用现有的控件描述符、字段绑定辅助与 XML 持久化。

- 复用点：控件描述符（`Tools/DescriptorGenerator`）、字段绑定 helper、保存/发布流程；
- 扩展点：页定义 XML 中新增 `<GeneratedFrom>`、`<Semantic>`、`<TakenOver>` 三个可选扩展节点（放在扩展区，老逻辑忽略）。

### 8.2 与部署/发布的集成

- 页面包生成后处于"草稿"，不立即生效；用户需显式点击"**部署页面包**"；
- 部署前执行"**一致性检查**"（Oracle APEX 的 Advisor 思想）：查找字段引用失效、权限冲突、必填缺失、脚本未部署等；
- 通过检查后，整体加入一次发布批次，形成 Manifest，与现有发布包衔接。

### 8.3 与权限系统的集成（重点）

生成阶段只**建议权限模板**，不强制授予任何权限，避免越权。集成要点如下：

| 权限维度 | 生成器行为 | 用户后续在哪配置 |
|----------|------------|------------------|
| 动作级权限（新建/编辑/删除/审核） | 生成"动作模板草案"，按场景给出默认推荐（如档案=新增+编辑+停用，单据=新增+编辑+提交+反审核） | 权限工作台应用模板 |
| 数据范围（本人/本部门/全公司） | 不生成具体范围，仅给出建议"适用角色"占位 | 权限工作台的"操作级范围" |
| 字段级可见/可改 | 按语义推断：草稿状态字段可改，已审批金额字段默认仅可见 | 权限工作台/流程节点权限 |
| 页面可见性（菜单） | 默认加入"业务对象"导航节点，但不授权给角色 | 菜单授权工作台 |
| 流程任务权限 | 不越权设置，仅在编辑页动作中预留"启动流程/处理任务"的挂点 | 流程模型 + 流程任务授权 |

### 8.4 与 nactivity（BPMN/DMN）集成

- 单据场景：编辑页自动预留"**启动流程**"挂点按钮，用户在向导中勾选后，按模板生成 `ProcStart` 动作；
- DMN 规则场景：查询页中对"计算指标"自动提示来源规则，支持点击查看解释；
- 详情页自动嵌入：当前记录流程轨迹（已有/可复用）、任务处理面板（如果当前用户有待办）。

### 8.5 与行业模块的集成

- 行业模块安装时自动运行"实体 → 生成页面包"的 S1–S6，形成草稿包；
- 安装向导最后一步显示草稿包，允许客户勾选不生成某些页面（如不需要打印模板）；
- 行业模块升级时，先对客户当前页面包做**差异比较**，再走 7.2 差异-采纳流程，避免升级直接覆盖客户定制。

## 9 数据模型设计

> **关于存储模式说明（重要）：**
> 本平台元数据**不以关系数据库表为主存储**，而是基于 `Sys.Core/Metadata/I*Repository` 接口提供 **两种可切换的 DI Provider**（启动时二选一注册，不运行时混合）：
> 1. **File Provider**（默认/单机/小型租户）——对应 [Sys.Core/Metadata/Repository](file:///d:/Project/MDD/9.0/src/Sys.Core/Metadata/Repository) 下的 [FileEntityDefineRepository.cs](file:///d:/Project/MDD/9.0/src/Sys.Core/Metadata/Repository/FileEntityDefineRepository.cs)、[FileFormDefineRepository.cs](file:///d:/Project/MDD/9.0/src/Sys.Core/Metadata/Repository/FileFormDefineRepository.cs)、[FormViewRepository.cs](file:///d:/Project/MDD/9.0/src/Sys.Core/Metadata/Repository/FormViewRepository.cs)，主存储为 `XlsTemplate/Schema/{entities,forms,reports,pageBundles}/` 目录下的 XML/JSON 文件。
> 2. **Redis Provider**（多实例/分布式/大租户）——对应 [Sys.Metadata.Redis](file:///d:/Project/MDD/9.0/src/Sys.Metadata.Redis) 下的 [AddRedisMetadataRepositoryExtension.cs](file:///d:/Project/MDD/9.0/src/Sys.Metadata.Redis/AddRedisMetadataRepositoryExtension.cs#L18-L31)，通过 `services.AddRedisMetadataRepository(configuration)` 把同接口替换为 Redis 实现：元数据以 **Hash / String（JSON）** 存入 Redis key（前缀 `{appId}:*`，见 [RedisConnection.cs](file:///d:/Project/MDD/9.0/src/Sys.Metadata.Redis/RedisConnection.cs#L55-L114)），表单 cshtml/js 等内容文件仍写磁盘，启动时自动执行 **SeedFromFileRepositoryAsync** File→Redis 增量迁移（见 [RedisEntityDefineRepository.cs#L463-L590](file:///d:/Project/MDD/9.0/src/Sys.Metadata.Redis/RedisEntityDefineRepository.cs#L463-L590)），并通过 [RedisCacheInvalidator.cs](file:///d:/Project/MDD/9.0/src/Sys.Metadata.Redis/RedisCacheInvalidator.cs#L41-L53) Pub/Sub `{appId}:entity:cache:invalidate` 通道做跨实例 L1 缓存失效。
> **Page Bundle 作为第 4 类元数据（与 Entity/Form/Report 平级），在两种 Provider 下都遵循同一套抽象与同一套 DI 注册**，具体映射方式见 9.1（File 结构）与 9.5（Redis 结构）。
> **SaaS 多租户隔离**：两种 Provider 都天然隔离——File 模式下每个租户独立部署的 WebApp.Core 进程各自的 [DomainModelBase.ModelRootPath](file:///d:/Project/MDD/9.0/src/Sys.Core/DomainModelBase.cs#L18-L35) 指向不同 `XlsTemplate/Schema/` 物理目录；Redis 模式下不同租户的 `CacheOptions.AppId/DatabaseNumber` 不同，key 前缀 `{appId}:*` 天然分开（见 [RedisConnection.cs#L40-L71](file:///d:/Project/MDD/9.0/src/Sys.Metadata.Redis/RedisConnection.cs#L40-L71)），**无需任何 tenant_id 列**。
> **跨进程发布链**：两种 Provider 在写完成功后都触发 `IModelChanged.Changed(...)` 事件（File 模式见原仓储实现，Redis 模式见 [RedisEntityDefineRepository.cs#L175](file:///d:/Project/MDD/9.0/src/Sys.Metadata.Redis/RedisEntityDefineRepository.cs#L175)、[RedisFormDefineRepository.cs#L112-L120](file:///d:/Project/MDD/9.0/src/Sys.Metadata.Redis/RedisFormDefineRepository.cs#L112-L120)），下游 etcd 推送/通知服务完全一致。

### 9.1 新增的仓储目录与文件结构

本平台所有元数据遵循"**L1 主索引 XML（DataSet 序列化，一行注册一个聚合根）→ L2 单项详情目录（每个聚合根子目录下存放自描述文件/快照）→ L3 引用已有资产（不重复存副本）**"的三层模式。页面包作为**第四类元数据**，与 `entities/`、`forms/`、`reports/` 平级。

> 对应代码参考：
> - L1/L2 读/写事务性模式参考 [FileEntityDefineRepository](file:///d:/Project/MDD/9.0/src/Sys.Core/Metadata/Repository/FileEntityDefineRepository.cs#L43-L128) 中 Entities.xml + {EntityName}.xml 的 DataTable 增删改 + `FileHelper.WriteAllText` 写法；
> - L3"只写引用不重复存副本"模式参考 [FileFormDefineRepository](file:///d:/Project/MDD/9.0/src/Sys.Core/Metadata/Repository/FileFormDefineRepository.cs#L19-L140) + [FormViewRepository](file:///d:/Project/MDD/9.0/src/Sys.Core/Metadata/Repository/FormViewRepository.cs#L23-L140) 中 FormId ↔ 视图定义的双目录分离；
> - 所有保存必须带 Foundatio 进程锁 + 保存前 oldFile 备份 + 失败还原的事务性保护（完全抄 [FileFormDefineRepository.Save](file:///d:/Project/MDD/9.0/src/Sys.Core/Metadata/Repository/FileFormDefineRepository.cs#L19-L86) 中 `lockObject` / `File.Copy(old_file, backup, true)` / catch 时 `File.Copy(backup, old_file, true)` 三段式）。

| 位置（相对 `XlsTemplate/Schema/`） | 层次 | 文件/目录 | 作用 | 对齐现有模式 |
|------------------------------------|------|-----------|------|--------------|
| `pageBundles/PageBundles.xml` | L1 主索引 | DataSet 序列化 XML | 每 `<PageBundle>` 行 = 一个页面包头；列：`bundle_id`、`name`、`source_kind`（Entity/Query）、`source_key`（实体名/脚本名）、`status`（草稿/已部署/停用）、`current_manifest_version`、`created_at`、`updated_at`、**`pages_json`**（引用的 form_id 列表 + page_kind=List/Edit/Detail/FilterAsset、route_path、taken_over_flags） | 等价于 `Entities.xml`、`Forms.xml`。读写方式完全照搬 Entities.xml 的 DataTable → 行修改 → `FileHelper.WriteAllText` 流程 |
| `pageBundles/{bundleId}/bundle.xml` | L2 单包头 | 单 Bundle 详情 XML | 该 Bundle 的完整自描述（便于离线拷贝/导入），内容与主索引行等价 + Bundle 级 `<StrategyOverride>` 可选节点 | 等价于 `entities/{EntityName}.xml`（单实体详情） |
| `pageBundles/{bundleId}/manifest-{NNN}.json` | L2 清单快照 | 纯 JSON 文件（001 递增） | 每次生成/同步产生一份，字段：`manifest_id`、`version_no`、`asset_list[]`（新/老控件清单、差异三态 +Δ−）、`source_snapshot{}`（实体字段快照 / 查询分析结果快照，用于差异比对）、`accept_plan{}`（用户逐项勾选记录）、`created_by`、`created_at`、`notes`、**可选 `form_backup`**（回滚所需的 forms/ 目录对应 formId 整包 ZIP 或内联快照） | 纯 JSON 存储，和 `form.Fields.ToJson()`（[FileFormDefineRepository.Save](file:///d:/Project/MDD/9.0/src/Sys.Core/Metadata/Repository/FileFormDefineRepository.cs#L93)）同套路，避免为深度嵌套结构做 DataSet JOIN；多份 manifest 天然就是回滚历史 |
| `pageBundles/{bundleId}/strategy-override.json`（可选） | L2 Bundle 级策略 | 纯 JSON | 比项目级/实体级更细的策略覆盖（一般只在 AI 推荐或场景差异化时用） | 等价于 `EntityDefine.Security` 扩展节点思路 |
| `config/page-generator-strategies.json`（可选，项目级） | L0 项目级策略 | 纯 JSON 配置文件 | 平台默认四种 Preset（档案/单据/申请/分析）的项目级覆盖 | 不进 Repository，只做配置文件读取 |
| `entities/{EntityName}.xml`（**已有文件，仅扩展节点**） | 扩展 | 在根 `<Table>` 下新增 `<PageGenStrategy preset="..." />`，与 `<Security>` / `<Rules>` / `<WideTableRefreshStrategy>` 同级 | 存储"这个实体默认用哪套生成策略" | 完全复用 [FileEntityDefineRepository.ReadSchema](file:///d:/Project/MDD/9.0/src/Sys.Core/Metadata/Repository/FileEntityDefineRepository.cs#L617-L688) 解析扩展节点的逻辑，加 3 行反序列化即可 |
| `forms/{FormId}/...`（**已有目录，不改结构，只写扩展属性**） | L3 引用 | 列表页/编辑页/详情页本身就是 FormDefine，复用 forms/ 目录；**不重复存储页面**。TakenOver / Semantic / GeneratedFrom 三个扩展标记直接写入 `Forms.xml` 行的 `Fields` JSON（`row["Fields"] = form.Fields.ToJson()`）或 `{FormId}/{FormId}.xml` 的 `<Define>` Schema 列 `<Extensions>` 子节点 | PageBundle.PagesJson 只存 `{ pageKind, formId, routePath, displayName, defaultEnabled }` 引用关系 + 是否 takenOver | 走推荐方案 A（塞 Fields JSON）或方案 B（塞 Define Schema Extensions），零新增文件，老版本读不懂即忽略，不会炸 |

### 9.2 SaaS 多租户下各租户"存在哪"——部署矩阵

| 角色 | 部署位置 | 元数据落点（ModelRootPath 自动解析） | Page Bundle 元数据落在哪？ |
|------|----------|---------------------------------------|----------------------------|
| 租户 A | 独立的 WebApp.Core 进程（目录 A） | `目录A/XlsTemplate/Schema/` | `目录A/XlsTemplate/Schema/pageBundles/...` 全在租户 A 自己目录，进程外不可见 |

### 9.4 为什么这样改是"最小侵入、可演进"的

1. **完全不推翻现有 Repository 双 Provider 模式**：PageBundle 作为第 4 类元数据，和 Entity/Form/Report 平级，I/F 接口定义在 Sys.Core/Metadata 中，File 实现放在 Sys.Core/Metadata/Repository，Redis 实现放在 Sys.Metadata.Redis（**对称**）—— 以后要加第 5 类 PrintTemplateBundle，完全套同样骨架；
2. **SaaS 多租户零改造**：File 模式下 ModelRootPath 天然隔离；Redis 模式下 `{appId}:*` key 前缀 + DatabaseNumber 天然隔离；不需要在任何地方加 `tenant_id`；
3. **部署链零新基建**：两条 Provider 都复用 IModelChanged 事件 → Redis 模式走 Pub/Sub 跨实例失效，File 模式走 etcd 文件 Watch + PageBundleOperator 推送，和实体/表单的发布链完全一致；
4. **回滚零新基建**：Manifest 存 JSON 快照天然就是"时间机器"—— File 模式在磁盘读 manifest-{NNN}.json，Redis 模式读 `{appId}:pagebundle_manifest:{bundleId}:{NNN}`，算法完全相同，只是 IO 层换了一行；
5. **TakenOver 扩展零新基建**：塞到现有 FormDefine.Fields 的 JSON 里，老版本和老逻辑读不到就忽略，不会炸。

## 12 与受控 AI 的结合点

AI 仅用于"**生成草稿和辅助理解**"，绝不直接写库或执行部署。所有 AI 输出都必须进入上述 S1–S7 的生成管道，经过 Advisor + 人工确认再落库。

### 12.1 建议的 AI 介入点

| 场景 | AI 做什么 | 谁最终生效 | 安全约束 |
|------|-----------|------------|----------|
| 实体建模时 | 推荐"适合的页面场景"（档案/单据/申请）与字段分组 | 用户在向导中确认 | 只读访问实体元数据，不写库 |
| 生成预览中 | 推荐字段是否进列表/筛选/编辑 | 差异采纳面板逐项确认 | 只输出 JSON 建议，不直接改 XML |
| 查询分析后 | 解释计算字段口径、建议筛选维度 | 用户采纳后写回策略覆盖 | 禁止解释中含真实敏感数据样例 |
| 差异同步中 | 推荐差异合并规则（新增全采纳/不触碰接管项等） | 用户点击合并计划 | 推荐可回溯，计划写入 Manifest |
| 权限建议 | 给出"建议动作模板"而非具体授权 | 管理员在权限工作台确认 | 不写权限存储，不改权限评估逻辑 |

### 12.2 AI 调用边界（Hard Rule）

- **Rule A**：AI 输出必须是结构化建议（JSON 或明确字段），不能是自由文本直接注入 XML；
- **Rule B**：AI 输出的控件类型、字段位置、分组，必须通过"生成器内部的策略校验"后才能进入预览；
- **Rule C**：任何涉及部署、权限授予、DDL 的操作，AI 只能提供"待确认的草稿"，执行必须走已有的人工确认 + 后台校验链。

## 14 风险与取舍

| 风险 | 可能性 | 影响 | 缓解策略 |
|------|--------|------|----------|
| 生成页面与现有空白画布风格不一致，造成两档页面并存 | 中 | 高 | 统一使用现有控件体系；生成器只调用 `createformcommand` 的现有能力 |
| TakenOver 机制复杂，用户忘记哪些是人工改动 | 中 | 中 | 设计器中增加"接管标记"徽标，悬浮显示来源与最后修改人 |
| 差异同步过于细，用户操作成本上升 | 中 | 中 | 提供"新增全采纳、接管跳过、标题格式统一"三个快捷模式 |
| 一次性生成的查询脚本性能不佳（未加索引/未拆分页） | 高 | 中 | Advisor 检查：列表页默认加分页 + 建议必要索引；复杂场景建议走查询模式 |
| AI 建议漂移导致同一实体多次建议不一致 | 中 | 低 | AI 建议走"策略缓存"，同一 Manifest 内同一场景只出一次可回溯建议 |
| 与行业模块升级冲突，覆盖客户定制 | 高 | 高 | 强制 P4 完成后再启用行业模块升级；升级前强制做差异备份 |

## 15 验收标准

### 15.1 功能验收

| 编号 | 验收点 | 通过标准 |
|------|--------|----------|
| F1 | 从实体生成成套页面 | 采购订单实体在 ≤3 分钟内得到可运行的"列表+编辑+详情+筛选器"四页草稿 |
| F2 | 从查询生成查询页 | "采购合同执行明细"脚本一键生成筛选+表格+个人视图的只读页 |
| F3 | TakenOver 生效 | 用户改动一个分组顺序后，下次同步不重置此顺序 |
| F4 | 差异-采纳 | 实体新增"交期"字段后，差异面板显示 +Δ，并可逐项采纳到三个页面 |
| F5 | Advisor 拦截 | 未部署实体时尝试部署页面包，被 Advisor 阻止并给出准确提示 |
| F6 | 权限不越权 | 生成页面包时只产生权限模板草案，不自动授予任何角色权限 |

### 15.2 非功能验收

| 维度 | 指标 |
|------|------|
| 性能 | 预览生成 ≤ 3 秒（普通实体，≤ 40 字段，2 个子表） |
| 一致性 | 同一实体字段标题在列表/编辑/详情/筛选器中一致率 100%（用户接管除外） |
| 兼容性 | 所有生成的 XML 可被原有设计器打开，不报错、不丢失内容 |
| 可维护性 | 生成器主逻辑 ≤ 3 个核心类 + 策略配置文件；策略覆盖不涉及代码改动 |

## 附：本次设计过程中的模型分工说明

为了保证"需求不跑偏、设计有深度、实现有抓手、文档可交付"，本方案在思考过程中采用了四种模型分工协作，对应 Trae 提示词规则中定义的角色如下：

| 分工 | 对应模型 | 在本次设计中承担的工作 | 关键产出 |
|------|----------|------------------------|----------|
| **需求分析** | **GPT-5.6-Terra** | 业务场景拆解、角色视角切换（实施人员/业务用户/管理员）、痛点识别、范围与非范围、验收标准初稿 | 第 1 章背景与目标、非目标；第 15 章的验收标准业务条目 F1–F6 |
| **方案设计** | **GPT-6-Astra** | 架构取舍、模块边界（生成器 vs 现有设计器 vs 部署链）、核心概念与数据模型、双生成模式、TakenOver + 差异-采纳机制、分阶段实施与风险控制；深度模块思想贯穿全文 | 第 3–10、13、14 章；第 11 章交互流程的结构与关键面板 |
| **编码/落盘（文档工程）** | **GPT-5.6-Sol** | 把设计内容按 Markdown 结构严格落盘：标题层级、表格、链接、术语一致性；不擅自扩展结论范围 | 本 Markdown 文档的技术实现：目录结构 / 表格 / 交叉引用 / 规范排版 |
| **文档润色与组织** | **GPT-5.6-Luna** | 统一术语、检查章节节奏与重复、补充非目标与边界说明、确认交付给业务/管理层也能阅读 | 第 1 章非目标、第 2 章原则表格化、第 15 章验收标准的拆分表达 |

**一句话总结：** Terra 负责把"要解决什么问题"讲清楚；Astra 负责把"怎么解、为何这么解"搭成架构骨架；Sol 负责把骨架钉成可审阅的正式文档；Luna 负责让文档读起来顺、不啰嗦。这四者在一个设计任务里是**串行协作关系**，而不是互相替代。
