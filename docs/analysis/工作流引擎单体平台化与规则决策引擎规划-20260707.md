## 1. 新规划结论

- `nactivity` 的核心定位不是复刻 `Activiti Cloud` 的云平台产品，而是作为 `.NET` 生态中的补充型工作流组件。
- `nactivity` 的交付形态坚持为 `NuGet` 组件包，不以独立工作流平台、独立低代码平台、独立认证中心、独立表单中心的形态建设。
- 身份验证与表单能力已在工作区 `src` 中实现，本文不再将其作为 `nactivity` 的规划主题展开。
- 新的发展主线应调整为：
  1. 做强工作流引擎内核与组件边界
  2. 做稳与 `src` 低代码平台的集成标准
  3. 以 `fork ScratchyDisk.DmnEngine` 源码为起点，沉淀自有 `Sys.Rules.DmnEngine` 组件库
  4. 做完整规则决策能力，并以接口设计驱动实现
  5. 最终形成轻量、可嵌入、可复用、可版本化发布的工作流组件体系

## 2. 项目定位重述

### 2.1 nactivity 的产品定位

- `nactivity` 是工作流引擎与配套组件集合。
- `nactivity` 面向的目标不是“自成一体的平台产品”，而是“为现有业务系统和低代码平台补充工作流能力”。
- `nactivity` 的核心价值在于：
  - BPMN 流程建模与解析
  - 流程定义部署与版本管理
  - 流程运行时推进
  - 人工任务与流程变量处理
  - 历史轨迹与运行时扩展点
  - 面向规则决策的流程集成挂点

### 2.2 nactivity 明确不承担的职责

- 不建设独立账号体系或统一认证中心。
- 不建设独立表单设计器、表单渲染器、表单元数据平台。
- 不建设完整低代码宿主平台。
- 不建设 Activiti Cloud 式的多服务云平台产品。
- 不以容器平台或独立部署方案为当前阶段重点。

### 2.3 与 Activiti 的关系

- `nactivity` 可以借鉴 `Activiti` 的引擎能力边界与 BPMN/规则相关思想。
- `nactivity` 不再以“功能上尽量复刻 Java 官方平台全貌”为目标。
- 新目标是：保留对工作流引擎核心能力的兼容思路，但在架构方向上转向 `.NET` 组件化集成。

## 3. 当前实际现状与规划依据

### 3.1 nactivity 当前代码组织特征

- 当前解决方案以类库项目为主，天然适合组件包形态演进。
- 当前已具备引擎、模型、REST 契约、客户端 SDK、样例宿主、测试工程等分层基础。
- 因此 `nactivity` 更接近“组件库 + SDK + 示例宿主”的结构，而不是“单一平台应用仓”。

### 3.2 src 低代码平台的实际承载现状

- 工作区 `src` 已经承担低代码宿主、设计器宿主与业务运行宿主职责。
- 因此 `nactivity` 的规划重点应放在“如何被宿主稳定引用”，而不是继续扩写宿主型能力。

### 3.3 新规划必须遵守的现实约束

- `src` 继续作为认证、表单、设计器宿主与业务运行宿主的统一集成层。

## 6. 与低代码平台的对接标准

### 6.1 流程设计集成标准

- `nactivity` 提供 BPMN 扩展属性约定。
- `src` 设计器宿主负责把这些扩展属性以 UI 方式呈现给用户。
- 设计器中的各类选择器与宿主交互能力由 `src` 负责承载，`nactivity` 只定义流程相关元数据约定。

### 6.2 运行时交互标准

- 流程发起前，由宿主完成业务上下文组装并调用 `nactivity`。
- 流程办理时，由宿主负责页面交互与业务数据准备，再调用 `nactivity` 办理接口。
- `nactivity` 返回流程状态、任务状态、变量结果和必要的规则执行结果，不直接负责页面渲染。

### 6.3 对接原则

- 优先使用现有能力和现有上下文传递机制，不新增为规划而规划的抽象接口。
- `nactivity` 与宿主之间优先通过稳定 DTO、配置项、流程扩展属性和调用约定协同。
- 已有简单可用的身份上下文处理机制保持现状，不作为本规划继续展开的重点。

## 8. 版本发布规范

### 8.1 发布原则

- 统一采用 `NuGet` 包发布。
- 统一采用语义化版本规则：`MAJOR.MINOR.PATCH`。
- 引擎核心、模型、契约、客户端应建立版本协同矩阵。

### 8.2 版本语义

| 版本位 | 含义 | 触发条件 |
| --- | --- | --- |
| `MAJOR` | 破坏性变更 | 公共接口不兼容、协议变更、行为语义变化 |
| `MINOR` | 向后兼容功能新增 | 新增扩展点、新增 API、新增 BPMN/规则能力 |
| `PATCH` | 缺陷修复 | Bug 修复、性能修复、文档修正、非破坏性优化 |

### 8.3 发布约束

- 每次发布必须附带：
  - 版本说明
  - 兼容性说明
  - 升级说明
  - 变更日志
- 对 `REST API`、`DTO`、扩展接口的破坏性变更必须进入 `MAJOR` 版本。
- 对规则决策相关公共契约或流程扩展属性的字段调整必须明确兼容策略。

### 8.4 包发布要求

- 包命名保持稳定，不频繁更名。
- 同一版本的相关包必须在同一批次发布。
- 禁止出现“引擎已升级但契约包未同步”的失配发布。
- 示例宿主的版本说明只作为参考，不参与核心组件版本裁决。
- 当前已在 `NActiviti/Directory.Build.props` 中建立统一版本入口，并通过 `NActiviti/scripts/pack-rule-decision-packages.ps1` 完成批次打包与 manifest 清单输出。

## 9. 规则决策引擎的新定位

- 不在 `nactivity` 中新增大型规则设计平台页面，设计端优先由 `src` 宿主承载。

### 9.4 IDecisionRuntimeService 接口定位

- `IDecisionRuntimeService` 是规则决策域的总入口接口。
- 该接口不只负责“执行一次决策”，还应覆盖决策定义、版本、发布、执行、解释、测试、导入导出、缓存失效、审计查询等完整生命周期。
- 规划上推荐将其视为“决策运行时门面接口”，内部再拆分为多个服务实现，但对宿主和工作流引擎暴露统一入口。

### 9.5 IDecisionRuntimeService 接口设计原则

- 原则 1：接口先行，先稳定契约，再逐步落地实现。
- 原则 2：所有外部可见能力统一走异步方法。
- 原则 3：执行类方法与管理类方法统一纳入同一决策门面，避免宿主侧拿到一组零散接口。
- 原则 4：结果对象必须支持“结果值 + 命中说明 + 调试信息 + 审计关联信息”。
- 原则 5：必须支持单规则集、决策表、规则链、版本发布与回滚，不只支持单次规则命中。

### 9.9 与 BusinessRuleTask 的集成要求

  - 支持单样例测试、批量测试、期望值断言
  - 支持命中规则高亮、执行路径解释、耗时展示
- 第五层：治理能力
  - 支持草稿、发布、回滚、比较、克隆、导入导出

- 当前已落地到产品级主编辑面的能力包括：
  - 基于图形画布的 `DRD` 节点拖拽定位
  - 依赖连线展示与选中高亮
  - 自动布局与适配视口
  - 节点属性数值精调（位置、尺寸、变量、规则/表达式）
  - 画布编辑与 XML 生成/反解析双向同步
- 当前已补齐到专业级工作台的能力包括：
  - 左侧最近使用决策清单
  - 专业工具箱与模板节点资产
  - 右侧缩略导航与模板资产区
  - `FEEL` 专业编辑区、上下文变量预览、变量点击插入、实时候选补全、函数签名参考、常用片段/函数模板与带行列定位的轻量诊断
  - 决策表输入列/输出列/默认规则/规则注释的结构化设计器
- 当前仍未完成的标准级能力包括：
  - 深入版 `FEEL` 语言服务、高亮与更完整的深层语义校验
  - 标准级 `dmn-js` 兼容与专业表格建模能力

### 9.14 与 BPMN 设计器的联动闭环

- `BusinessRuleTask` 属性面板中应新增：
  - 决策选择器
  - 版本选择器
  - 输入映射编辑器
  - 输出映射编辑器
  - 决策测试入口
  - 决策设计入口
- 对于顺序流条件、服务任务等场景，后续也可支持复用同一决策引用机制，避免规则只绑定 `BusinessRuleTask`。
- 流程设计器保存时，应记录流程对决策的引用清单，供发布校验与影响分析使用；正式部署、草稿保存与删除流程时都应同步刷新该索引。
- 流程调试器中，应能查看节点执行时对应的决策输入、输出、命中规则和版本号。

- 前端建模层优先参考 `camunda-dmn-js` 与 `dmn-js`，因为这两者更贴近浏览器嵌入式建模场景。

### 9.17 DMN 设计器页面结构与交互流程

#### 9.17.1 页面结构规划

- 推荐在现有工作流设计工作区中增加 `DMN` 设计工作区，采用与 `BPMN` 设计器一致的三栏式结构。
- 推荐页面结构如下：

| 区域 | 主要内容 | 说明 |
| --- | --- | --- |
| 左侧资源区 | 决策目录树、分类、标签、版本列表、搜索栏 | 用于选择决策与查看引用关系 |
| 中央画布区 | `DRD` 画布、决策表画布、表达式编辑区 | 用于完成主要建模操作 |
| 右侧属性区 | 决策属性、输入输出定义、命中策略、规则说明 | 用于完成配置与治理属性编辑 |
| 底部调试区 | 测试样例、执行结果、命中解释、校验消息 | 用于联调、测试、排错 |
| 顶部操作栏 | 新建、保存、校验、测试、发布、回滚、导入导出 | 用于完成完整生命周期操作 |

#### 9.17.2 页面模式规划

- 页面至少支持以下五种主模式：
  - `DRD` 模式：用于组织输入数据、决策节点与依赖关系
  - 决策表模式：用于维护输入列、输出列、规则矩阵、默认规则与命中策略
  - 表达式模式：用于维护 `Literal Expression`、上下文变量、实时候选、函数签名参考、常用片段与 `FEEL` 定位诊断
  - 测试模式：用于录入样例并查看执行结果
-  - 发布模式：用于查看发布准备、版本差异摘要、版本替换路径、影响流程分层、失败原因聚合、内容差异摘要、规则级新增/删除/修改分类摘要与预览、规则/表达式/XML 预览、支持差异项回跳工作区节点并自动切换到对应页签、展示统一的当前 Compare 来源摘要与失效后恢复引导、在删节点后提示 Compare 上下文已失效、当前命中 compare 条目高亮且在切定义/切版本/手动切节点或切规则行时自动清理过期导航状态、规则项高亮到矩阵行并在决策表模板页持续对照期望规则与当前矩阵规则且在规则矩阵结构性变更后重新对齐命中行、表达式项在 FEEL 编辑区持续对照期望值与当前值且与规则/XML 提示区保持一致字段布局、XML 项可持续对照 compare 行与当前设计页命中行，且三类提示区的状态文案统一收敛到组件方法维护的双栏可视化 compare 工作台、支持从当前 DRD/模板/XML 编辑结果正式保存草稿并刷新版本上下文，且保存前会校验 XML 并在非法时引导回 DRD/XML 页签修正、建议发布说明、治理摘要、影响范围与版本状态
- 同一决策对象在不同模式间切换时，应保持上下文不丢失。

#### 9.17.3 页面级交互流程

1. 用户从流程设计器中的 `BusinessRuleTask` 点击“设计决策”或“选择决策”
2. 系统打开 `DMN` 设计工作区，并自动定位到目标 `DecisionKey`
3. 用户在 `DRD` 或决策表中编辑规则
4. 用户点击“校验”，系统返回结构校验、语法校验、命中策略校验结果
5. 用户点击“测试”，输入样例数据并查看命中规则、输出结果与解释信息
6. 用户保存草稿或发布版本
7. 发布成功后，系统回填流程节点可用的 `DecisionKey`、`VersionTag` 与版本状态
8. 流程设计器重新校验节点绑定状态，并允许继续发布流程

#### 9.17.4 关键交互细节

- 在 `BusinessRuleTask` 未绑定决策时，属性面板应提供：
  - 新建决策
  - 选择已有决策
  - 查看最近使用决策
- 在已绑定决策时，属性面板应提供：
  - 查看当前绑定版本
  - 切换版本
  - 打开设计器
  - 打开测试页
  - 查看最近发布记录
- 当前工作区已补齐：
  - 图形画布拖拽与选中联动
  - 自动布局与适配视口
  - 属性表单与画布双模编辑
  - 最近使用决策、专业工具箱与缩略导航
  - 模板资产快捷生成与 `FEEL` 片段/函数模板辅助
  - 基于版本状态、流程引用与执行失败记录的细粒度治理提示
  - 发布准备视图、集中门禁摘要、目标版本审计基线、版本替换路径、失败原因聚合、内容差异摘要、规则级新增/删除/修改分类摘要与预览、支持差异项回跳工作区节点、规则项高亮到矩阵行、表达式项在 FEEL 编辑区持续对照期望值与当前值且 XML 项可持续对照 compare 行与当前设计页命中行的双栏可视化 compare 工作台，以及可复制发布模板
  - 决策表列设计器与原始规则文本双向同步
  - 字面表达式专业编辑区、上下文变量点击插入与带行列位置的 FEEL 诊断面板
- 当决策已被多个流程节点复用时，设计器应提示影响范围。
- 当用户尝试发布流程但引用了未发布的决策版本时，系统应阻止发布并给出可操作提示。

#### 9.17.5 页面联动事件规划

| 事件 | 触发方 | 接收方 | 作用 |
| --- | --- | --- | --- |
| `decision-selected` | BPMN 属性面板 | DMN 工作区 | 打开指定决策 |
| `decision-saved` | DMN 工作区 | BPMN 属性面板 | 刷新绑定信息 |
| `decision-published` | DMN 工作区 | BPMN 设计器/发布器 | 更新版本状态与引用校验 |
| `decision-test-completed` | DMN 工作区 | 流程调试器 | 展示测试结果与解释信息 |
| `decision-reference-changed` | BPMN 设计器 | 流程发布器 | 刷新流程引用清单 |

#### 9.17.6 页面级校验规则

- `DRD` 视图应校验：
  - 是否存在孤立决策
  - 是否存在循环依赖
  - 是否缺少必要输入节点
- 决策表视图应校验：
  - 输入列与输出列是否完整
  - 命中策略与规则配置是否冲突
  - 数据类型是否一致
- 表达式视图应校验：
  - `FEEL` 语法是否有效
  - 是否引用不存在的输入变量
  - 是否存在不可达表达式
  - 当前工作区已支持轻量级变量引用检查、上下文变量预览、括号/引号匹配检查、条件表达式完整性检查、不完整运算符检查以及带行列位置的诊断提示
- 决策表模板与节点详情页已支持：
  - 命中策略候选限定
  - `UNIQUE/ANY/RULE ORDER` 等命中策略冲突提示
  - 输入列、输出列、默认规则与规则注释的结构化建模
  - 规则缺项与空输出即时校验
- 发布前应统一校验：
  - 决策是否保存
  - 决策是否通过语义校验
  - 被流程引用的版本是否可用

### 9.18 BusinessRuleTask 与 DMN 字段绑定协议

#### 9.18.1 绑定目标

- `BusinessRuleTask` 必须能够以稳定协议绑定到一个明确的决策定义与决策版本。
- 该协议既要能支撑设计期建模，也要能支撑运行时执行与调试回溯。

#### 9.18.2 推荐绑定字段

| 字段名 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `DecisionKey` | `string` | 是 | 决策定义唯一键 |
| `DecisionName` | `string` | 否 | 决策显示名称，便于设计器展示 |
| `DecisionType` | `string` | 是 | 决策类型，如 `DecisionTable`、`LiteralExpression`、`RuleSet` |
| `VersionTag` | `string` | 否 | 指定绑定版本；为空时按默认发布版本解析 |
| `BindingMode` | `string` | 是 | 绑定模式，如 `LatestPublished`、`FixedVersion` |
| `InputMappings` | `json` | 否 | 流程变量到决策输入的映射 |
| `OutputMappings` | `json` | 否 | 决策输出到流程变量的映射 |
| `ExecutionMode` | `string` | 否 | 执行模式，如同步执行、解释模式、调试模式 |
| `TraceEnabled` | `bool` | 否 | 是否记录命中解释信息 |
| `FallbackPolicy` | `string` | 否 | 决策执行失败时的处理策略 |
| `TimeoutMs` | `int` | 否 | 决策执行超时时间 |

#### 9.18.3 输入映射协议

- `InputMappings` 推荐支持以下映射来源：
  - 流程变量
  - 固定值
  - 表达式计算值
  - 业务上下文对象字段
- 推荐结构：

```json
[
  {
    "inputName": "amount",
    "sourceType": "processVariable",
    "sourceValue": "amount"
  },
  {
    "inputName": "applicantDept",
    "sourceType": "contextPath",
    "sourceValue": "initiator.deptId"
  },
  {
    "inputName": "priority",
    "sourceType": "constant",
    "sourceValue": "high"
  }
]
```

#### 9.18.4 输出映射协议

- `OutputMappings` 推荐支持以下目标：
  - 单一流程变量
  - 多个流程变量
  - 统一决策结果对象
- 推荐结构：

```json
[
  {
    "outputName": "approved",
    "targetType": "processVariable",
    "targetValue": "approved"
  },
  {
    "outputName": "nextAssignee",
    "targetType": "processVariable",
    "targetValue": "nextAssignee"
  }
]
```

#### 9.18.5 绑定模式协议

| 模式 | 含义 | 适用场景 |
| --- | --- | --- |
| `LatestPublished` | 始终绑定最新已发布版本 | 规则频繁迭代、流程不希望频繁改版 |
| `FixedVersion` | 固定绑定指定版本 | 强审计、强合规、流程与规则需严格固化 |
| `VersionTagPreferred` | 优先绑定指定标签，不存在时失败 | 灰度发布、环境差异控制 |

#### 9.18.5.1 文件级版本仓储约定

- 当前阶段 `Sys.Rules.DmnEngine` 采用“文件仓储 + 版本标签命名”作为最小可执行版本发布协议。
- 裸文件命名：`{decisionKey}.dmn`，用于未显式启用版本路由的基础定义。
- 版本化文件命名：优先支持
  - `{decisionKey}.{versionTag}.dmn`
  - `{decisionKey}-{versionTag}.dmn`
- `FixedVersion`：只解析指定 `versionTag` 对应的版本化文件。
- `VersionTagPreferred`：优先解析指定 `versionTag` 对应的版本化文件，不存在时直接失败。
- `LatestPublished`：在同一 `decisionKey` 的版本化文件中按版本号倒序选择最高版本；若不存在任何版本化文件，则回退到裸文件。
- 推荐版本标签采用语义化风格，如 `v1.0.0`、`v1.2.3`。

#### 9.18.6 失败处理策略

| 策略 | 含义 | 建议场景 |
| --- | --- | --- |
| `FailProcess` | 决策失败则流程失败 | 强一致性审批、核心风控 |
| `UseDefault` | 决策失败时使用默认输出 | 非关键辅助判断 |
| `SkipTask` | 跳过规则任务继续后续流程 | 仅用于弱依赖场景 |
| `ManualIntervention` | 转人工处理 | 高风险业务、需人工兜底 |

#### 9.18.6.1 失败策略扩展参数协议

- `fallbackPolicy=UseDefault` 时，默认输出统一通过 `qh:option` 承载，命名规则为 `defaultOutput.{outputName}`。
- `fallbackPolicy=UseDefault` 命中后，运行时将把这些选项还原为决策输出，再按 `outputMappings` 或默认回写规则写入流程变量。
- `fallbackPolicy=ManualIntervention` 时，人工介入上下文与 BPMN 错误并行生效：
  - 写入流程变量：变量名由 `manualIntervention.variableName` 指定，默认值为 `decisionManualIntervention`
  - 传播 BPMN 错误：错误码由 `manualIntervention.errorCode` 指定，默认值为 `DMN_MANUAL_INTERVENTION`
  - 错误消息：可由 `manualIntervention.errorMessage` 指定，未配置时使用运行时默认文案
- `qh:option` 采用最小结构：

```xml
<qh:option name="defaultOutput.approved" value="true" />
<qh:option name="manualIntervention.variableName" value="manualReviewContext" />
<qh:option name="manualIntervention.errorCode" value="DMN_REVIEW_REQUIRED" />
```

#### 9.18.7 设计期展示协议

- 在属性面板中，绑定协议应以可视化表单方式呈现，而不是让用户直接编辑原始 JSON。
- 推荐展示分组：
  - 基本信息
  - 决策绑定
  - 输入映射
  - 输出映射
  - 执行选项
  - 错误处理
- 设计器保存时再统一序列化为流程扩展属性。

#### 9.18.8 运行时解析协议

1. 引擎执行到 `BusinessRuleTask`
2. 根据 `DecisionKey` 与 `BindingMode` 解析可执行决策版本
3. 根据 `InputMappings` 组装执行入参
4. 调用 `IDecisionRuntimeService.ExecuteAsync`
5. 根据 `OutputMappings` 将结果写回流程变量
6. 根据 `TraceEnabled` 决定是否写入命中解释
7. 若执行失败，则按 `FallbackPolicy` 处理

#### 9.18.9 审计与调试字段

- 运行时建议额外记录以下信息：
  - `DecisionExecutionId`
  - `DecisionVersion`
  - `MatchedRuleIds`
  - `HitPolicy`
  - `ElapsedMs`
  - `InputSnapshot`
  - `OutputSnapshot`
- 这些字段应可被流程调试器和历史审计页直接消费。

### 9.19 IDecisionRuntimeService 配套 DTO 详细定义

#### 9.19.1 DTO 设计原则

- DTO 设计应服务于三类场景：
  - 设计期定义与发布
  - 运行时执行与解释
  - 审计查询与调试回放
- DTO 命名应保持分层清晰：
  - `Request` 用于入参
  - `Descriptor` 用于定义与元数据描述
  - `Result` 用于执行、测试、导入导出结果
  - `Query` 用于分页查询条件
- 同一 DTO 尽量只承担单一职责，避免把定义、执行、审计字段混在一个对象中。

#### 9.19.2 决策定义类 DTO

| DTO | 用途 | 关键字段 |

#### 9.19.13 运行时解析规则与数据职责

- `FixedVersion`：
  - 要求 `version_tag`
  - 直接按 `(decision_key, version_tag)` 取版本表
- `VersionTagPreferred`：
  - 要求 `version_tag`
  - 先按 `(decision_key, version_tag)` 查找
  - 不存在则直接失败，不回退
- `LatestPublished`：
  - 先查 `decision_version.is_published = true`
  - 按 `version_number desc` 取第一条
  - 若无已发布版本，则视为未发布定义，不建议回退到草稿
- 执行日志必须记录：
  - 请求版本标签
  - 实际命中版本标签
  - 绑定模式
  - 输入输出快照
  - 命中规则与追踪明细

#### 9.19.14 宿主装配与配置策略落地

- 当前宿主启动链已在 `AddProcessEngine(...)` 内部接入规则仓储与 DMN 运行时注册：

- 当前装配策略如下：
  1. 宿主总会注册 `IDecisionRuntimeService`，保证 `BusinessRuleTask` 与宿主应用均可获得统一决策运行入口。
  2. 若存在 `DecisionRulesStore` 配置节，则优先按该配置注册数据库版规则仓储：

  - 为后续从文件版平滑迁移到数据库版提供过渡路径

  - 引擎启动时会先保持既有 `schema.version` 严格校验语义

  - 当核心 schema 版本已匹配，但 `decision_definition / decision_version / decision_execution_log / process_decision_reference` 任一扩展表缺失时，会输出非阻断告警，并按数据库类型提示执行对应升级脚本
  - 为便于宿主日志平台检索，当前告警统一使用前缀 `[decision-schema-warning]`，并固定事件号：
    - `700001`：schema 版本落后
    - `700002`：规则扩展表缺失
  - 当前还提供了运行期只读查询接口 `GET Api/v1/workflow/process-deployer/schema-status`，用于输出：
    - `expectedSchemaVersion / actualSchemaVersion`
    - `missingTables`
    - `status`
    - `recommendedAction`

#### 9.19.19 发布前 DMN 定义合法性校验落地

- 当前规则治理链已在以下两条“进入生效态”的路径中接入发布前校验：
  - `PublishVersionAsync(...)`
  - `RollbackVersionAsync(...)`
- 校验策略为：
  1. 仅当 `sourceFormat` 为空或等于 `DMN` 时启用
  2. 先识别 DMN 版本，并兼容 Camunda 1.3 导出扩展语义
  3. 通过 `DmnParser.ParseString(...)` 完成 XML 解析
  4. 通过 `DmnDefinitionFactory.CreateDmnDefinition(...)` 完成模型合法性校验
- 当前不在 `SaveDraftAsync(...)` 中阻断草稿保存，原因是：
  - 设计期草稿可能处于未完成状态
  - 前端设计器保存过程需要允许阶段性不完整资产
  - 真正需要强约束的是“发布为生效版本”这一动作
- 当校验失败时，治理服务会抛出统一错误消息：
  - `决策 {decisionKey} 的版本 {versionTag} 在发布前 DMN 校验失败：...`
- 该校验的直接收益：
  - 避免非法 DMN 版本进入 `Published` 状态
  - 避免运行时首次命中时才暴露结构性错误
  - 使版本发布、回滚与执行审计形成更完整的质量门禁

### 9.20 BPMN/DMN 扩展属性 XML 存储约定

#### 9.20.1 设计目标

- 设计期配置必须能稳定序列化到 `BPMN XML`。
- `BusinessRuleTask` 与 `DMN` 绑定信息必须可被前端设计器、后端引擎、调试器、发布器共同消费。
- 存储约定应尽量兼容当前 `bpmn-js + moddle extension` 的扩展方式，不破坏现有设计器体系。

#### 9.20.2 总体原则

- 流程主模型仍以标准 `BPMN` 为主。
- `DMN` 绑定信息通过 `extensionElements` 承载，不污染标准属性。
- 简单标量优先存成独立属性项，复杂映射优先存成结构化扩展节点。
- 同一节点上的规则决策配置必须集中存储，避免分散在多个扩展块中难以维护。

#### 9.20.3 推荐命名空间

- 推荐沿用当前自定义扩展命名空间风格，新增一组 `qh` 前缀下的决策扩展定义。
- 推荐命名示例：
  - `qh:decisionBinding`
  - `qh:inputMapping`
  - `qh:outputMapping`
  - `qh:decisionOption`

#### 9.20.4 BusinessRuleTask 扩展结构

- 推荐在 `bpmn:businessRuleTask` 下增加如下扩展结构：

```xml
<bpmn:businessRuleTask id="Activity_RuleApprove" name="审批规则判断">
  <bpmn:extensionElements>
    <qh:decisionBinding
      decisionKey="expense.approval"
      decisionName="费用审批规则"
      decisionType="DecisionTable"
      versionTag="v1.2.0"
      bindingMode="FixedVersion"
      executionMode="Sync"
      traceEnabled="true"
      fallbackPolicy="ManualIntervention"
      timeoutMs="3000">
      <qh:inputMappings>
        <qh:inputMapping inputName="amount" sourceType="processVariable" sourceValue="amount" />
        <qh:inputMapping inputName="deptId" sourceType="contextPath" sourceValue="initiator.deptId" />
      </qh:inputMappings>
      <qh:outputMappings>
        <qh:outputMapping outputName="approved" targetType="processVariable" targetValue="approved" />
        <qh:outputMapping outputName="nextAssignee" targetType="processVariable" targetValue="nextAssignee" />
      </qh:outputMappings>
    </qh:decisionBinding>
  </bpmn:extensionElements>
</bpmn:businessRuleTask>
```

#### 9.20.5 元素级字段约定

| XML 元素/属性 | 含义 | 对应设计期字段 |
| --- | --- | --- |
| `qh:decisionBinding@decisionKey` | 决策唯一键 | `DecisionKey` |
| `qh:decisionBinding@decisionName` | 决策名称 | `DecisionName` |
| `qh:decisionBinding@decisionType` | 决策类型 | `DecisionType` |
| `qh:decisionBinding@versionTag` | 目标版本标签 | `VersionTag` |
| `qh:decisionBinding@bindingMode` | 绑定模式 | `BindingMode` |
| `qh:decisionBinding@executionMode` | 执行模式 | `ExecutionMode` |
| `qh:decisionBinding@traceEnabled` | 是否记录解释 | `TraceEnabled` |
| `qh:decisionBinding@fallbackPolicy` | 失败策略 | `FallbackPolicy` |
| `qh:decisionBinding@timeoutMs` | 超时时间 | `TimeoutMs` |
| `qh:inputMapping` | 输入映射项 | `InputMappings` |
| `qh:outputMapping` | 输出映射项 | `OutputMappings` |

#### 9.20.6 输入映射 XML 约定

- `qh:inputMapping` 推荐字段：
  - `inputName`
  - `sourceType`
  - `sourceValue`
  - `defaultValue`
  - `dataType`
- 示例：

```xml
<qh:inputMapping
  inputName="priority"
  sourceType="constant"
  sourceValue="high"
  defaultValue="normal"
  dataType="string" />
```

#### 9.20.7 输出映射 XML 约定

- `qh:outputMapping` 推荐字段：
  - `outputName`
  - `targetType`
  - `targetValue`
  - `overwrite`
- 示例：

```xml
<qh:outputMapping
  outputName="approved"
  targetType="processVariable"
  targetValue="approved"
  overwrite="true" />
```

#### 9.20.8 设计器存储策略

- 属性面板编辑时使用结构化表单。
- 保存时统一写入 `extensionElements`。
- 加载时由 `workflowModeler` 或同类封装层负责：
  - 解析 `qh:decisionBinding`
  - 解析输入输出映射子节点
  - 回填到属性面板的表单模型
- 对于未知字段，设计器应尽量保留原样，避免保存时丢失扩展信息。

#### 9.20.9 引擎解析策略

1. 解析 `BusinessRuleTask` 节点
2. 读取 `extensionElements` 中的 `qh:decisionBinding`
3. 将 XML 扩展结构反序列化为运行时配置对象
4. 组装 `DecisionExecutionRequest`
5. 调用 `IDecisionRuntimeService`
6. 将执行结果与解释信息写回流程上下文

#### 9.20.10 版本兼容策略

- 新增扩展字段时，应保持旧 XML 仍可读取。
- 删除扩展字段时，应至少保留一个兼容周期。
- 设计器与引擎对扩展节点的解析应采用“忽略未知字段、保留原始节点”的兼容策略。
- 若扩展结构发生破坏性调整，应同步提升相关 `NuGet` 包主版本号。

#### 9.20.11 DMN 模型侧存储建议

- `DMN` 本体仍建议以标准 `DMN XML` 存储。
- 设计器辅助信息可拆分为两层：
  - 标准 `DMN XML`
  - 宿主附加元数据，如标签、分类、最近测试样例、发布说明
- 不建议把全部设计期元数据强行写入 `DMN XML`，以免与标准模型混杂。

### 9.22 IDecisionRuntimeService C# 接口正式稿

#### 9.22.1 接口定位

- `IDecisionRuntimeService` 作为对外总门面接口，用于被工作流引擎、宿主系统、管理接口统一调用。
- 规划上允许内部拆为多个服务，但对外先稳定一组主接口，以降低集成复杂度。

#### 9.22.2 正式接口稿

```csharp
public interface IDecisionRuntimeService
{
    /// <summary>
    /// 创建决策定义。
    /// </summary>
    Task<DecisionDefinitionDescriptor> CreateDefinitionAsync(
        CreateDecisionDefinitionRequest request,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// 更新决策定义。
    /// </summary>
    Task<DecisionDefinitionDescriptor> UpdateDefinitionAsync(
        UpdateDecisionDefinitionRequest request,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// 获取单个决策定义。
    /// </summary>
    Task<DecisionDefinitionDescriptor?> GetDefinitionAsync(
        string decisionKey,
        string? versionTag = null,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// 查询决策定义列表。
    /// </summary>
    Task<PagedResult<DecisionDefinitionDescriptor>> QueryDefinitionsAsync(
        DecisionDefinitionQuery query,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// 发布指定决策版本。
    /// </summary>
    Task<DecisionVersionDescriptor> PublishVersionAsync(
        PublishDecisionVersionRequest request,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// 回滚到指定决策版本。
    /// </summary>
    Task<DecisionVersionDescriptor> RollbackVersionAsync(
        RollbackDecisionVersionRequest request,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// 比较两个决策版本差异。
    /// </summary>
    Task<DecisionVersionCompareResult> CompareVersionsAsync(
        string decisionKey,
        string sourceVersionTag,
        string targetVersionTag,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// 执行单次决策。
    /// </summary>
    Task<DecisionExecutionResult> ExecuteAsync(
        DecisionExecutionRequest request,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// 批量执行决策。
    /// </summary>
    Task<IReadOnlyList<DecisionExecutionResult>> ExecuteBatchAsync(
        BatchDecisionExecutionRequest request,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// 获取决策解释结果。
    /// </summary>
    Task<DecisionExplanationResult> ExplainAsync(
        DecisionExplanationRequest request,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// 执行决策测试。
    /// </summary>
    Task<DecisionTestResult> TestAsync(
        DecisionTestRequest request,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// 导入决策定义。
    /// </summary>
    Task<DecisionImportResult> ImportAsync(
        DecisionImportRequest request,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// 导出决策定义。
    /// </summary>
    Task<DecisionExportResult> ExportAsync(
        DecisionExportRequest request,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// 查询决策执行日志。
    /// </summary>
    Task<PagedResult<DecisionExecutionLogDescriptor>> QueryExecutionLogsAsync(
        DecisionExecutionLogQuery query,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// 获取指定执行记录的输入输出快照。
    /// </summary>
    Task<DecisionExecutionSnapshot?> GetExecutionSnapshotAsync(
        string executionId,
        CancellationToken cancellationToken = default);

    /// <summary>
    /// 使指定决策缓存失效。
    /// </summary>
    Task InvalidateCacheAsync(
        DecisionCacheInvalidationRequest request,
        CancellationToken cancellationToken = default);
}
```

#### 9.22.3 子接口拆分建议

- 为便于内部实现解耦，建议在实现层进一步拆分为：
  - `IDecisionDefinitionService`
  - `IDecisionVersionService`
  - `IDecisionExecutionService`
  - `IDecisionTestService`
  - `IDecisionImportExportService`
  - `IDecisionAuditService`
  - `IDecisionCacheService`
- 对外可继续只暴露 `IDecisionRuntimeService`，由门面统一编排。

#### 9.22.4 与工作流引擎的调用约定

- `BusinessRuleTask` 运行时仅调用：
  - `ExecuteAsync`
  - 必要时调用 `ExplainAsync`
- 流程设计器与发布器主要调用：
  - `GetDefinitionAsync`
  - `QueryDefinitionsAsync`
  - `PublishVersionAsync`
  - `CompareVersionsAsync`
- 测试与审计页面主要调用：
  - `TestAsync`
  - `QueryExecutionLogsAsync`
  - `GetExecutionSnapshotAsync`

#### 9.22.5 异常模型建议

- 推荐统一定义以下异常语义：
  - `DecisionDefinitionNotFoundException`
  - `DecisionVersionNotFoundException`
  - `DecisionValidationException`
  - `DecisionExecutionException`
  - `DecisionImportException`
- 对外 API 层不要直接暴露底层规则引擎异常原文，应统一转换成稳定错误码与消息。

#### 9.22.6 返回模型约束

- `ExecuteAsync` 与 `TestAsync` 的返回对象必须包含足够的调试信息，但不应强制把所有快照大对象直接塞入主结果。
- 对于大体量输入输出快照，建议通过 `ExecutionId` 延迟查询。
- 这样既能兼顾前端调试体验，也能避免运行时响应对象过重。

### 9.23 TypeScript 解析模型与前端读写约定

#### 9.23.1 设计目标

- 前端设计器需要一组稳定的 `TypeScript` 模型来承接三类数据：
  - `moddle` 反序列化后的节点扩展数据
  - 属性面板表单编辑态数据
  - 调用后端决策接口时的请求数据
- 模型设计应区分：
  - `BPMN extension` 原始结构
  - 页面表单模型

### 9.25 DMN 执行内核源码纳管策略

#### 9.25.1 选型结论

- `DMN` 执行内核不采用“直接引用 `ScratchyDisk.DmnEngine` 官方 `NuGet` 包”的方式。
- 明确采用“直接 `fork ScratchyDisk.DmnEngine` 源码，并封装为 `Sys.Rules.DmnEngine` 自有组件库”的路线。
- 该路线的目标不是简单复制第三方代码，而是将 `DMN` 执行能力纳入 `nactivity` 自身的可控边界。

#### 9.25.2 采用该路线的原因

- 若直接依赖上游 `NuGet` 包，后续出现解析兼容、语义差异、性能瓶颈、日志缺口时，修复节奏完全受制于上游。
- 当前项目要形成完整开发体验，后续必然需要补充：
  - `BusinessRuleTask` 运行时适配
  - 统一异常模型
  - 审计日志
  - 执行解释
  - 缓存治理
  - 与前端设计器字段协议的稳定映射
- 这些能力更适合在源码级纳管后统一改造，而不是在第三方 `NuGet` 包外层持续做脆弱绕接。

#### 9.25.3 目标组件定位

- 目标组件名称：`Sys.Rules.DmnEngine`
- 目标角色：`nactivity` 规则决策子域中的标准 `DMN` 执行内核组件
- 对外定位：
  - 作为 `nactivity` 自有规则决策体系的底层执行实现
  - 对外不直接暴露上游项目命名空间
  - 对上层统一服务于 `IDecisionRuntimeService`

#### 9.25.4 推荐项目形态

| 项目/包 | 职责 | 对外暴露原则 |
| --- | --- | --- |
| `Sys.Rules.DmnEngine` | 承接 `fork` 后的 `DMN` 解析与执行内核 | 尽量不直接暴露第三方来源命名空间 |
| `Sys.Bpm.Rules.API` | 决策接口、DTO、查询模型、错误码 | 作为正式公共契约 |
| `Sys.Bpm.Rules.Core` | 决策应用服务、版本治理、测试、审计 | 调用 `Sys.Rules.DmnEngine` |
| `Sys.Bpm.Rules.Rest` | 对外管理与测试 API | 不直接依赖内核细节 |

#### 9.25.5 源码纳管原则

- 保留上游许可证与版权声明。
- 明确保留上游来源链与 `fork` 说明。
- 源码纳管后，优先做以下收口：
  - 命名空间调整
  - 项目名调整
  - 包名调整
  - 日志与异常模型接入
  - 与当前 `nactivity` 解决方案的构建规范对齐
- 不建议将上游源码直接散拷贝到多个现有项目中，应以独立项目方式纳入解决方案。

#### 9.25.6 命名空间与项目命名建议

- 解决方案内项目建议命名：
  - `Sys.Rules.DmnEngine`
  - `Sys.Rules.DmnEngine.Tests`
  - `Sys.Rules.DmnEngine.Benchmarks`（可选）
- 命名空间建议统一为：
  - `Sys.Rules.DmnEngine`
  - `Sys.Rules.DmnEngine.Parser`
  - `Sys.Rules.DmnEngine.Execution`
  - `Sys.Rules.DmnEngine.Feel`
  - `Sys.Rules.DmnEngine.Diagnostics`
- 不建议继续沿用上游公开包名作为最终发布名，以避免后续对外认知混淆。

#### 9.25.7 第一阶段改造范围

- 第一阶段不是重写整个 `DMN` 引擎，而是完成“可用、可接、可维护”的纳管改造。
- 第一阶段建议完成：
  1. 建立 `fork` 仓库并保留上游基线
  2. 重命名项目、程序集、命名空间为 `Sys.Rules.DmnEngine`
  3. 确认当前代码可在目标 `.NET` 版本下稳定构建
  4. 补充 `BusinessRuleTask` 场景所需的执行结果映射
  5. 增补统一异常类型与日志埋点
  6. 增补面向 `IDecisionRuntimeService` 的适配层

#### 9.25.8 后续增强范围

- 纳管完成后，再逐步增强：
  - `DMN XML` 兼容性修复
  - `FEEL` 语义增强
  - 规则命中解释能力
  - 执行快照
  - 决策缓存
  - 前端设计器调试支持
  - 测试样例回放能力

#### 9.25.9 与上游同步策略

- 采用“上游基线 + 本地增强分支”的维护模式。
- 不追求频繁同步上游，而是按版本批次评估：
  - 是否有重要修复
  - 是否有标准兼容增强
  - 是否会破坏既有接口约定
- 每次同步必须先通过：
  - `DMN XML` 兼容测试
  - 关键决策表回归测试
  - `BusinessRuleTask` 集成回归测试
- 当前已补充：

  - 本地扫描报告输出目录 `artifacts/reports/rule-dmn-upstream-sync`

#### 9.25.10 发布策略

- 对外正式发布名采用 `Sys.Rules.DmnEngine`。
- 组件发布时不再直接暴露 `ScratchyDisk.DmnEngine` 依赖关系。
- 上游能力作为内部实现来源处理，对外只强调：
  - `nactivity` 自有规则执行内核
  - `NuGet` 组件包交付
  - 与 `Sys.Bpm.Rules.API` 的版本协同
- 当前已为 `Sys.Bpm.Rules.API`、`Sys.Bpm.Rules.Core`、`Sys.Rules.DmnEngine`、`Sys.Rules.DmnEngine.Adapter` 补齐基础包元数据、说明文件与符号包配置，并完成带统一版本号与 manifest 的本地批次打包验证。
- 当前已补充 `NActiviti/scripts/publish-rule-decision-packages.ps1`，可将批次包整理为 `publish-ready` 目录并在提供发布源参数后执行正式推送。

  - 分层测试与样例集

- `CLAUDE.md` 中明确给出了核心架构分层、测试工程结构、命中策略、`FEEL` 类型映射与执行流水线，这种信息量通常不是临时演示项目会具备的。[CLAUDE.md](https://raw.githubusercontent.com/Scratchydisk/ScratchyDisk.DmnEngine/master/CLAUDE.md)
- `nuget.md` 与 `readme.md` 明确列出了：
  - 全量标准命中策略
  - `DRD`
  - 表达式缓存
  - 线程安全定义
  - Programmatic Builder
  - `FEEL` 完整解释能力  
  这表明其目标是通用执行内核，而不是单一演示场景。[nuget.md](https://raw.githubusercontent.com/Scratchydisk/ScratchyDisk.DmnEngine/master/nuget.md) [readme.md](https://raw.githubusercontent.com/Scratchydisk/ScratchyDisk.DmnEngine/master/readme.md)

  - 不是 `demo`

  - 但也不是已经完全成熟到可以直接外包风险给上游的稳定内核

## 11. 风险与控制

| 风险 | 说明 | 控制措施 |
| --- | --- | --- |
| 边界回摆 | 继续把宿主能力拉回 `nactivity` | 通过职责矩阵和规划边界约束范围 |
| 组件失焦 | 一边想做组件，一边又走平台产品路线 | 所有新需求先判断是否符合 `NuGet` 组件定位 |
| 包版本失配 | 模型、引擎、契约、客户端版本不同步 | 建立统一版本矩阵与批次发布规则 |
| 集成耦合过深 | `nactivity` 直接绑定 `src` 内部实现 | 只依赖稳定约定和公共契约，不依赖宿主细节 |
| 上游源码漂移 | `fork` 后与上游差距越来越大，难以同步 | 采用上游基线分支与内部增强分支双轨维护 |
| 第三方痕迹外泄 | 最终组件仍暴露上游命名空间或模型 | 用 `Sys.Rules.DmnEngine` 统一对外命名与契约收口 |
| 规则能力过度膨胀 | 轻量规则运行时演变成大型规则平台 | 坚持“服务流程编排”的能力边界 |
| 决策接口失稳 | 过早变更 `IDecisionRuntimeService` 导致宿主升级成本高 | 先冻结核心 DTO 与方法族，再渐进扩展 |
| 设计器割裂 | BPMN 与 DMN 分属两套孤立体验，导致配置成本高 | 统一工作区、统一属性面板入口、统一测试入口 |

## 12. 最终建议

- 现阶段最重要的不是继续把 `nactivity` 往“独立平台”方向扩写，而是把它明确收束为 `.NET` 生态中的轻量工作流组件库。
- 新规划应始终围绕三条主线展开：
  - 做强引擎内核
  - 做清组件边界
  - 做稳与 `src` 的集成标准
- 在这个前提下，规则决策能力可以继续建设，但必须坚持：
  - 组件包交付
  - 宿主集成优先
  - 不向宿主平台能力回侵
