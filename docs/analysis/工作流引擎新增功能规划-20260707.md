## 1. 规划目标

- 本文档聚焦“补齐官方缺失后，如何结合当前 .NET 技术栈继续产品化增强”。
- 规划目标不是简单复制 Java 版本，而是形成更适合当前项目的企业级 .NET 工作流平台能力。

## 3. 重点规划项

### 3.1 统一身份与组织中心适配层

- 业务价值：
  - 支撑岗位、部门、角色、汇报关系、代理、兼职组织的统一办理人解析。
  - 让前端“办理人规则”从页面配置能力升级为平台能力。
- 技术可行性：
  - 当前前端已有办理人规则配置入口。
  - 当前后端已有身份链接、候选人与外部用户代理的能力基础。
- 落地建议：
  - 增加 `Identity Adapter`。
  - 将审批人解析、候选组展开、代理规则统一下沉到后端策略层。

### 3.2 统一表单引擎

- 业务价值：
  - 打通流程设计、发起页、办理页、变量映射闭环。
  - 形成平台级表单能力，支撑低代码配置。
- 技术可行性：
  - 前端已有属性扩展与节点表单配置入口。
  - 后端已有 `FormField`、`FormProperty` 模型基础。
- 落地建议：
  - 统一支持 `StartForm`、`TaskForm`、`ReadonlyForm` 三类视图。
  - 建立变量绑定、校验规则、权限控制与组件字典协议。

### 3.3 运维中心

- 业务价值：
  - 降低生产事故处理门槛。
  - 把引擎层已有的 Job 能力变成平台能力。
- 技术可行性：
  - 当前引擎层已有 `ManagementService`、Job、Timer、DeadLetter 管理基础。
- 落地建议：
  - 第一阶段：提供查询、失败原因查看、重试、死信恢复。
  - 第二阶段：增加告警、批量处置、运行健康面板。

### 3.4 审计中心与过程时间线

- 业务价值：
  - 支撑合规审计、流程复盘、问题追踪与监管要求。
- 技术可行性：
  - 当前已有历史服务与事件基础。
- 落地建议：
  - 增加统一事件模型：实例创建、任务创建、认领、审批、驳回、回退、终止、变量变化。
  - 提供实例时间线、节点轨迹和事件回放视图。

### 3.5 实时通知与任务订阅

- 业务价值：
  - 提高待办提醒、催办、流程状态刷新效率。
- 技术可行性：
  - .NET 技术栈天然适合使用 `SignalR`。
- 落地建议：
  - 先以任务状态变更事件驱动前端实时更新。
  - 后续再演进成独立通知中心。

### 3.6 连接器中心

- 业务价值：
  - 支撑 ERP、MES、CRM、短信、邮件、外部 API 等跨系统编排。
- 技术可行性：
  - 当前已有 WebApi 任务行为雏形，可继续标准化。
- 落地建议：
  - 设计连接器注册规范、执行协议、幂等策略、重试补偿模型。
  - 与流程事件总线结合，逐步形成异步编排体系。

## 4. 分阶段路线

### 4.1 P0

1. 统一身份与组织中心适配层
2. 统一表单引擎
3. 运维中心
4. 流程版本治理与发布流水线
5. 收口当前半成品：
   - 前端 `copy()`、`SCRIPT`、`MESSAGES`、属性空方法
   - 后端 `return null`、客户端 `NotImplementedException`

### 4.2 P1

1. 审计中心与过程时间线
2. SignalR 实时通知
3. 连接器中心
4. 读模型/报表中心
5. SLA/超时/催办/升级策略
6. OpenTelemetry 可观测性

### 4.3 P2

1. DMN/规则决策引擎
2. 流程变更影响分析
3. 多租户隔离增强
4. 流程资产中心与模板市场

## 5. 落地原则

- 优先补齐“引擎层已存在、平台层未闭环”的能力。
- 优先做对当前业务收益最大的能力，而不是一次性照搬 Activiti Cloud 全套架构。
- 先完成单体平台化，再按职责拆分出 Query、Audit、Notification、Connector 等服务。

## 6. 结论

- 当前系统具备很好的引擎底座，后续重点应转向平台化与产品化。
- 最有价值的演进顺序是：
  - 先补 `Identity + Form + Management`
  - 再补 `Audit + Notification + Connector + Read Model`
  - 最后推进 `DMN + 影响分析 + 多租户增强 + 资产中心`
