## 4. 重点缺失项分析

### 4.1 身份体系缺失

- 现状：
  - 前端已有办理人选择器，但主要依赖业务规则与外部用户查询。
  - 后端存在身份链接、候选用户/组等零散能力，但未形成 `IdentityService` 产品边界。
- 业务影响：
  - 难以沉淀统一组织架构审批模型。
  - 候选组、岗位池、部门级授权无法形成平台标准能力。
  - 与企业 IAM/SSO 的对接缺少标准层。
- 原 Java 逻辑：
  - 官方通过 `IdentityService` 管理 `User`、`Group` 与 `Membership`。
  - 候选人与身份链接能力围绕该服务展开。

### 4.2 表单体系缺失

- 现状：
  - 前端属性面板支持配置起始表单、节点表单。
  - 后端模型层存在 `FormField`、`FormProperty`，但缺少独立表单服务与运行时表单接口。
- 业务影响：
  - 设计器可配置，但发起页与办理页不能依赖统一平台生成。
  - 表单与流程变量映射缺少标准化。
- 原 Java 逻辑：
  - 官方 `FormService` 提供启动表单、任务表单及表单属性访问能力。

### 4.3 运维管理闭环缺失

- 现状：
  - 引擎层已有 Job、Timer、DeadLetter、Async Executor 等完整基础设施。
  - REST/UI 管理台缺失。
- 业务影响：
  - 生产故障定位依赖人工查库或代码级排查。
  - 失败重试、死信恢复、定时作业治理难以标准化。
- 原 Java 逻辑：
  - 官方 `ManagementService` 暴露作业查询、执行、迁移、失败处理等能力。

### 4.4 Cloud 平台能力缺失

- 现状：
  - 当前系统仍是单体式工作流平台。
  - 未见独立查询服务、审计服务、通知服务、连接器服务。
- 业务影响：
  - 难以支撑高并发读写分离。
  - 跨系统事件编排与实时通知能力不足。
- 原 Java 逻辑：
  - Cloud 体系将 `Runtime`、`Query`、`Audit`、`Notification`、`Connector` 分拆为独立服务。

## 5. 影响范围评估

| 影响维度 | 主要受影响能力 | 风险等级 | 说明 |
| --- | --- | --- | --- |
| 业务建模 | 表单、组织架构审批、连接器编排 | 高 | 会限制复杂流程快速落地 |
| 运行稳定性 | Job、Timer、DeadLetter 管理 | 高 | 缺少平台化运维手段 |
| 产品化能力 | Identity、Form、评论附件、候选组 | 高 | 影响企业级 BPM 平台完整度 |
| 平台扩展性 | Query/Audit/Notification/Connector | 中高 | 影响未来云原生与平台化升级 |
| 用户体验 | SCRIPT/MESSAGES、实时通知 | 中 | 影响设计器完整度与协同体验 |

## 6. 结论

- 当前 .NET 迁移版已完成传统 Activiti 核心引擎能力的大部分迁移。
- 最主要的问题不是“没有引擎能力”，而是“平台外围能力未完全产品化”。
- 后续若以企业级工作流平台为目标，应优先补齐：
  - Identity
  - Form
  - Management 运维平台
  - 评论/附件/候选组等平台闭环
  - Cloud 风格的读模型、审计、通知与连接器体系
