# nactivity 性能问题分析与改进建议

> 本文档基于对全仓库（NActiviti/、Smart.Sql/、Sys.Expression/）的静态代码分析整理，所有问题均附文件与行号证据。分析未做运行时基准测量，落地前建议对重点项目用 dotnet-trace / BenchmarkDotNet 量化验证。

## 一、总体结论

项目存在四个层面的系统性性能问题，且多处相互叠加：

1. **表达式链路无缓存（最严重）**：SpEL 表达式每次求值都全量 ANTLR 重解析，且运行时反复创建表达式对象、每次求值全量深拷贝变量上下文。这条链路贯穿网关条件、用户任务属性、监听器、SmartSql 动态 SQL 条件标签，是引擎第一大热点。
2. **异步作业体系名存实亡**：假线程池（同步串行执行）+ 作业锁过期时间设置失效（Java→C# 移植 bug，锁立即过期）+ 异步作业在请求线程上同步执行，三者叠加导致作业吞吐极低，且存在重复执行与乐观锁冲突风暴。
3. **数据访问层固定开销大**：SmartSql 每次查询全量重建 SQL（缓存被注释掉）、反射调用反序列化器、值类型结果走 Newtonsoft JSON 往返、每查询新建会话。
4. **缓存机制多处失效或畸形**：流程定义信息缓存"命中也每次回源查库"、DMN FEEL 静态缓存以随机 Guid 为键只增不减、部署缓存 limit 模式直接抛异常。

## 二、P0 级问题（改动小、收益全链路，建议优先）

### P0-1. SpEL/EL 表达式解析全链路无缓存

**证据**

- `Sys.Expression/Expressions/Expression.cs:77-125`：`ParseWithAntlr4` 每次调用都新建 `AntlrInputStream / ExpressionLexer / CommonTokenStream / ExpressionParser / SpringExpressionVisitor`，**没有任何解析结果缓存**（Spring.NET 原版有 `expressionCache`，移植时丢失）。
- 调用入口：`Sys.Expression/Util/ExpressionManager.cs:44-50`，每次 `GetValue` 都 `Expression.Parse(expr)`。
- 引擎触发点：`NActiviti/Sys.Bpm.Engine/Engine/impl/el/ValueExpression.cs:161`，即**每一个 `${...}` 表达式每次求值**。
- SmartSql 触发点：`Smart.Sql/SmartSql/Configuration/Tags/Tag.cs:103-106`，每个 `<IsNotEmpty>/<IsEqual>/<For>` 条件标签求值都走同一 ANTLR 链路。热路径映射文件中条件标签数量：Task.xml 47 个、Execution.xml 138 个、HistoricTaskInstance.xml 约 320 个——一次历史任务查询可触发上百次 ANTLR 解析。

**影响**：ANTLR 全管线（lexer+parser+AST+visitor）是微秒~毫秒级且高分配操作；节点级访问器缓存（`PropertyOrFieldNode.cs:56`）因 AST 每次重建而完全失效，属性解析反射也随之重复。

**建议**：在 `Expression.Parse` 层加 `ConcurrentDictionary<string, IExpression>` 解析缓存，key 为表达式文本。注意：**不能简单声称“AST 不可变可安全共享”**——AST 的*结构*不可变，但节点带惰性初始化的 accessor 缓存（见 `PropertyOrFieldNode.cs:56` 的 `accessor` 字段），跨线程共享时必须对节点缓存加锁（已加 `syncObject`），求值状态则保存在每次新建的 `EvaluationContext` 中。**缓存本身必须设容量上限（LRU 或计数上限 + FIFO 逐出）**：静态表达式总量有限，但 SmartSql 动态 SQL 与 `${}` 文本可能随参数拼接而基数无限，无界字典会内存单调增长——这与本文档 P2 对 FEEL/`_definitionCache` “只增不减”的批评一致。`ConcurrentDictionary.GetOrAdd` 工厂可能并发重入致同一表达式解析多次，属可接受浪费。一处改动，引擎 EL 与 SmartSql 两条链路同时受益。（已落地：`Expression.cs` 已加带 FIFO 逐出的有界缓存。）

### P0-2. 运行时反复 CreateExpression + 每次求值深拷贝全部变量　`⚠️ 部分落地`

**证据**

- `NActiviti/Sys.Bpm.Engine/Engine/impl/el/ExpressionManager.cs:69-76`：`CreateExpression` 无缓存，且每次都 `ProcessEngineServiceProvider.Resolve<IExpressionFactory>()`（:81-87）。上游 Activiti 在 BpmnParse 阶段创建一次表达式存入 behavior 复用，本移植版在运行时重建。
- 热路径调用点：`UserTaskActivityBehavior.cs:139,154,166,178,198,225,241,260,336,362,376,398,423,457`（每创建一个用户任务新建 ~15 个表达式对象）；`ConditionUtil.cs:30`（每条出线条件每次流转新建）；`SkipExpressionUtil.cs:62`、`TakeOutgoingSequenceFlowsOperation.cs:243`、`CallActivityBehavior.cs:101,132,169`、`TimerUtil.cs:47-67` 等。
- `el/ValueExpression.cs:149-162`：循环体内反复访问 `execution.Variables`——`.Keys` 一次、循环内索引 N 次、传参一次，N 个变量 = **N+2 次完整变量收集**（`VariableScopeImpl.cs:75-91,241-269` 每次都 `CollectVariables` 沿父作用域链重建字典，O(N²)）；随后全量拷贝进 `ExpandoObject`，JToken 变量逐个 `ToObject` 深转（`ValueExpression.cs:171-202`）。
- `ValueExpression.cs:118-147`：每次求值用未编译正则 Replace 重建表达式串，字符串分配密集。

**影响**：O(变量数 × 表达式数)，变量越多越糟，且与 P0-1 叠加。

**建议**：表达式文本→对象缓存（配合 P0-1 的 AST 缓存收益最大）；一次求值内 `Variables` 只取一次快照；避免 ExpandoObject 全量深拷贝（直接以变量字典为求值上下文）；正则加 `Compiled`。

> `⚠️ 部分落地`：现码 `ExpressionManager.cs:82-104` 已加 `expressionCache`（ConcurrentDictionary）与 `expressionFactory` 实例缓存；`el/ValueExpression.cs:154-166` 已将 `execution.Variables` 取一次快照复用；`el/ValueExpression.cs:21` 的 `EXPR_PATTERN` 已加 `RegexOptions.Compiled`。**仍未落地**：`:152-164` 依旧把全部变量 `ToObject` 后拷贝进 `ExpandoObject`（未改为直接以变量字典为上下文），变量多时仍有一次全量深转开销。

### P0-3. SmartSql 查询结果反序列化走反射 MethodInfo.Invoke　`✅ 已落地`

**证据**：`Smart.Sql/SmartSql/SmartSqlMapper.cs:130-137`（Query）与 `:156-161`（QuerySingle）——引擎几乎所有映射都带 `resultType`/`ResultMap`，因此每次查询都执行 `GetMethod` 查找 + `MakeGenericMethod` + `MethodInfo.Invoke`（含参数装箱数组分配），结果再 `Cast<T>().ToList()` 二次物化。

**影响**：每次 DB 查询的固定反射开销。

**建议**：按 `(deserializerType, resultType)` 缓存编译后的委托（Expression.Compile 或 DynamicMethod），一次编译永久复用；消除多余的 Cast/ToList。

> `✅ 已落地`：现码 `SmartSqlMapper.cs:124-171` 已按 `(DeserializerType, ResultType)` 缓存 `Func<...>` 委托（`_toEnumerableDelegateCache`/`_toSingleDelegateCache`），委托内直接物化为 `List<resultType>`，类型匹配时免去 `Cast<T>().ToList()`。上方证据行号（:130-137/:156-161）已过时。

### P0-4. ProcessDefinitionInfoCache 命中也每次回源查库　`✅ 已落地`

**证据**：`NActiviti/Sys.Bpm.Engine/Engine/impl/persistence/deploy/ProcessDefinitionInfoCache.cs:106-142`——`RetrieveProcessDefinitionInfoCacheObject` 即使缓存命中也无条件执行 `FindProcessDefinitionInfoByProcessDefinitionId(...)` 查库比对 revision。`resources/activiti.cfg.json:59` 默认 `enableProcessDefinitionInfoCache=true`，此时 `ConditionUtil.cs:20`、`UserTaskActivityBehavior.cs:100`、`ServiceTaskExpressionActivityBehavior.cs:65`、`ScriptTaskActivityBehavior.cs:91`、`ClassDelegate.cs:234` 都经 `Context.GetBpmnOverrideElementProperties`（`Context.cs:168-177`）触发该缓存。

**影响**：引擎每推进一步都多一次数据库往返，缓存形同虚设。

**建议**：命中时直接返回缓存对象；**但不能裸“命中直接返回”而缺失失效机制**——必须配短 TTL 或订阅 `ProcessDefinitionInfo` 变更/部署事件主动失效，否则 `DynamicBpmnService` 的运行时改写将永久不可见（陈旧读 bug）。

> `✅ 已落地`：现码 `ProcessDefinitionInfoCache.cs:128-133` 已改为命中且 `DateTime.UtcNow - LastRevisionCheckTime < RevisionCheckInterval` 时直接返回缓存、不再回源；超过间隔才查库校 revision（短 TTL 方案）。另 `Add`（:98-103）已补 `Size = 1`、`Clear`（:110-115）已改 `Interlocked.Exchange` 原子替换，順带修复了 P2 部署缓存的 Size/并发缺陷。

### P0-5. 作业锁过期时间设置失效（一行移植 bug，兼具正确性问题）

**证据**：`Engine/impl/cmd/AcquireJobsCmd.cs:53-58`、`Engine/impl/cmd/AcquireTimerJobsCmd.cs:54-59`——`cl.AddMilliseconds(lockTimeInMillis)` 返回值被丢弃（Java 可变 Calendar → C# 不可变 DateTime 移植失误），`job.LockExpirationTime` 实际等于**当前时间**，锁立即过期。

**影响**：作业一开始执行就"过期"：① `ResetExpiredJobsRunnable`（每 60s）把正在执行的作业重置回收；② 集群下其他节点立即重复获取同一作业 → 同一作业并发重复执行 + 乐观锁冲突风暴（每次冲突还触发 RetryInterceptor 重试等待）。

**建议**：`cl = cl.AddMilliseconds(lockTimeInMillis);`。

### P0-6. 假线程池：作业全部同步串行执行 `✅ 已落地`

**证据**

- `Engine/impl/asyncexecutor/ThreadPoolExecutor.cs:53-56`：`Execute(ThreadStart)` 直接 `runnable.Invoke()` 在调用方线程上同步执行；`Shutdown()` 空实现、`AwaitTermination()` 恒返回 true。`DefaultAsyncJobExecutor` 的 `corePoolSize=2 / maxPoolSize=10 / queueSize=100`（`DefaultAsyncJobExecutor.cs:35-50`）全部是无效配置。
- 叠加 `Engine/impl/jobexecutor/AsyncJobAddedNotification.cs:32-37`：`asyncExecutorActivate=true` 时，"异步延续"实际在提交请求的线程上同步跑完后续整段流程，HTTP 请求延迟 = 作业执行时长；失败后作业已被锁 5 分钟（`DefaultJobManager.cs:600-601`），要等 reset 线程捡回，失败重试延迟被放大。
- `ExecuteAsyncJob.cs:206-234` 针对 RejectedExecutionException 的回退逻辑实际会吞掉作业抛出的任意异常并 Unacquire。

**影响**：作业体系名义异步并行，实际"单线程串行 + 锁立即过期 + 请求线程同步执行"。

**建议**：以 `BlockingCollection<T>` + 工作者线程（或 Task 调度）实现真实 `IExecutorService`，恢复并行执行与背压；配合 P0-5 与 P1-7（调大批次）。

> **定级说明**：本项虽收益关键，但改动为线程池重写、**含明确的行为语义变化**（作业真正并行执行），并非 P0 段首所述“改动小、无行为语义变化”的主体；路线图已将其排入**第二阶段**（需集成测试回归）。可视作“关键但非低风险”，与其余 P0 分开对待。
>
> （`✅ 已落地`：三条证据均已修复——① `ThreadPoolExecutor.cs` 已重写为真实有界线程池（`BlockingCollection<ThreadStart>` + 工作线程，`Execute`/`Shutdown`/`AwaitTermination` 均真实实现）；② `DefaultAsyncJobExecutor.ExecuteAsyncJob`（:192-241）已改为 `executorService.Execute(runnable)` 异步入队，作业在池工作线程执行、不再占用请求线程；③ 拒绝回退仅捕获 `RejectedExecutionException`（:210）并 `Unacquire` 解锁、不再吞掉任意异常。配合 P1-7 批量已调至 10。多节点部署仍需按该行为变化做并发作业集成回归）
